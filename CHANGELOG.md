# Changelog

## [1.15.0] — 2026-08-10

### Added

- **The mask review window gains the viewer's filmstrip** — a series that contains clips now shows one thumbnail per image between the picture and the slider, decoded in the background with the current image outlined; click a thumbnail to jump straight to it, exactly as in the viewer. A coloured stripe under each thumbnail states what the run's masking will do to that image — green masked, amber masked by fallback rectangles on an ultrasound image with no calibrated region, blue marked as needing none, red cannot be masked and would fail — resolved by the export's own rules and re-resolved live as rectangles are drawn, undone or exempted. For an echo study this turns finding the analysis screens that need hand masking from a scrub through every clip into a glance along the strip

### Changed

- **A masked file stays compressed on export** — masking still has to decompress a file to write its pixels, but the masked image is now re-encoded on the way out instead of leaving as uncompressed Explicit VR Little Endian. A JPEG 2000 Lossless or JPEG Lossless source is recompressed straight back into its own transfer syntax — the export keeps the encoding, and roughly the size, it arrived in. A lossily-compressed source (JPEG Baseline, JPEG Extended, lossy JPEG 2000) is re-encoded to JPEG 2000 Lossless instead: re-entering the lossy format would degrade every pixel in the image a second time, while a lossless encode of the already-decoded samples adds no loss at all — the transfer syntax changes, the image does not. Measured on a JPEG Baseline echo study, a fully masked export shrinks from 16.5× the stored size to 2.1×. Every re-encoded frame is decoded again and compared bit for bit against the masked pixels before it is written, so a defective encode can only ever fall back to the old uncompressed behaviour, never ship altered pixels. The completion summary and Activity Log report the three outcomes — recompressed to own syntax, re-encoded to JPEG 2000 Lossless, left uncompressed — as separate counts
- **A compressed file that masking inspects but leaves untouched now exports byte-identical** — when the header could not settle whether a scoped region applied, the file was decompressed to find out and then exported uncompressed even though nothing was masked. Its original pixel data is now restored verbatim in that case, so only files whose pixels actually changed are ever re-encoded

## [1.14.0] — 2026-08-08

### Added

- **Burned-in PHI can be masked out of exported images** — a modification profile gains *mask regions* (new dicomqr-only `maskregions` key), which blank rectangles of the image itself on the way out. Tag rules cannot reach a patient banner an ultrasound machine printed into the pixels; this is what removes it. Geometry is stored as fractions of the image rather than pixel coordinates, so one profile covers a study whose series differ in size, and rectangles round outward — half a row of leftover text is still PHI. A second mode, *outside the ultrasound region*, takes its geometry from the file's own region calibration sequence instead of a hand-drawn rectangle: banner layout varies by vendor and preset, but the calibrated image region is always stated, and a duplex study's two panes mask to their bounding box so the gap between them keeps its content. An ultrasound image that declares no region falls back to the profile's rectangles, and fails rather than exporting unmasked only when there are none to fall back on (see below); a file of another modality is simply not what that rule describes and passes through it. Regions can be set per modality, where they replace the profile's rather than adding to them. This replaces dicomtool's `maskrows`, removed in 1.13.0, which could only blank whole rows from the top of the image — and remains a deliberate divergence: dicomtool ignores `maskregions`
- **Mask regions are edited in Preferences** — the profile editor gains a *Pixel masking* section listing one row per region: a mode, and for a rectangle its position and size as percentages of the image (the geometry fields grey out for the ultrasound rule, which takes its geometry from the file). Percentages are what the editor shows and fractions are what the profile stores, so an unedited profile round-trips to the same numbers rather than accumulating decimals. Regions can also be set on a per-modality override, which is where they belong when one modality's images are laid out differently from another's; the override list shows the count alongside its other rules. The Modification dialog lists the regions a run will apply, and names any modality whose override replaces them — shown rather than editable, because geometry belongs to the profile, but never silent
- **Mask rectangles can be drawn on an image instead of measured** — *Pick from image…* in the profile editor opens any DICOM file and lets areas be dragged out on it directly, with Undo last and Clear all; what is drawn snaps to that image's pixel grid, so the stored geometry is the area marked to the nearest pixel rather than an approximation carrying screen-coordinate noise. The window states the file's size and modality, and for an ultrasound image whether it declares a calibrated region — which is what decides whether that file needs a rectangle at all
- **A run's images can be reviewed and masked one by one** — *Review masking…* in the Modification dialog reads every selected file's header and presents the run **series by series** in acquisition order — for an ultrasound study that is clip by clip, each clip shown at its middle frame. A slider beneath the image scrubs through the current series and Previous/Next step between series; the arrow keys step one image and Ctrl with an arrow steps a series. Images decode in the background while scrubbing, so the slider never waits on a file, and files that cannot be read are counted in the window's caption rather than silently left out. Every control sits under the image in the order the work is done — scrub, change series, see which image is on screen, mark it, apply — and the running description of what masking will do to the current image sits beside the button that commits it. Each image is shown with the areas that will be blanked drawn on it, resolved by the export's own code so the two cannot disagree. Tick *Draw rectangles* and drag across the image to mark an area, choosing with *Applies to* how far it reaches — **this image only** (the default), *Images of this size* (same modality and dimensions — and, for ultrasound, whether the file states its own region — with like images in other series included), or every image in the run. Image-only is the default because the images needing a hand-drawn rectangle are usually the ones whose layout is unique: an ultrasound study's analysis screens differ from each other, and blanking the same area across them destroys the report content the export exists to keep. *Needs no masking* records that an image was reviewed and requires none, which is what lets an ultrasound image with no stated region export instead of failing. *Undo* takes back what this session added and never a region the profile arrived with. Regions marked here apply to that run only, like every other control in the dialog. The section is shown even for a profile that masks nothing — a study whose analysis screens carry a banner is exactly when the absence of masking needs to be noticed
- **An ultrasound image with no calibrated region falls back to the profile's rectangles** — such files are usually analysis or measurement screens rather than captures, and are often exactly what a de-identified dataset needs to keep. Where the profile defines a rectangle, it masks those files instead of the rule that could not be resolved: the banner goes, the quantitative results stay, and the file is exported rather than failed. The substitution is counted in the completion summary and logged per file, since those images were masked by geometry measured on other images. With no rectangle to fall back on the file still fails rather than exporting unmasked
- Masked pixels are filled with black **as the file's photometric interpretation defines it** — the maximum stored value for MONOCHROME1, `Y=0` with neutral chroma for YBR, the darkest palette entry for PALETTE COLOR. A constant zero would paint a white or green box, which reads as an intact annotation rather than as a redaction
- **Masking a compressed image decompresses it on export** — the application has decoders but no encoders, so a masked file can only leave uncompressed. Rather than fail every compressed file, a profile with mask regions decompresses what it must to Explicit VR Little Endian, even when its Output transfer syntax is *As stored*, and the run reports how many files this happened to in the completion summary and the Activity Log. Chroma-subsampled ultrasound stored uncompressed is the one case that still needs the option set by hand, and says so
- **A file that cannot be masked is never exported** — masking writes pixels, so anything that stops it (compressed pixel data with no built-in decoder, an unusable sample layout, an ultrasound image with no stated region and no rectangle to fall back on) fails that file and reports why, rather than writing out an image with the banner intact. Every other file in the run still exports
- **Overlay planes can be removed on export** — a profile gains *Remove overlay planes* (new dicomqr-only `nooverlays` key), which drops every overlay-plane group (6000–60FE) from the exported files. Overlay Data is a bitmap channel a vendor can draw patient text into — the application's own viewer renders these planes — and nothing else reaches it: removing it tag by tag would take dozens of entries across sixteen repeating groups, *Remove private tags* never touches it (overlay groups are even), and pixel masking writes only the pixel data itself. The option sits beside Remove private tags in the profile editor and the Modification dialog, is profile-wide like the other scalar options, and is off unless asked for — a profile shared with dicomtool keeps its meaning

### Changed

- **The Modification panel is a window you can move, resize and scroll** — it was a fixed panel sized to its contents, so a profile with many set values and a long list of removed tags could make it taller than the screen, leaving Modify… and Cancel below the bottom edge where they could not be clicked. Its contents now scroll with the buttons pinned beneath them, so it fits any screen, and it can be dragged aside like the profile editor and the Activity Log
- **Set values are listed in the order the profile stores them** — the profile editor sorted the rows by tag number, which filed the shipped profile's Patient Name behind a blank Accession Number and rewrote a hand-ordered profiles.json into sorted order on Apply even when nothing was edited. The rows now follow the profile — the order its author chose, and the order the Modification dialog already presents — with tags added through the picker joining at the end
- **The shipped default profiles are reworked** — `base-deident` now leads its set values with Patient Name (and the Patient ID that follows it), removes overlay planes, and skips SR, PR, KO and OT objects rather than exporting them; `base-deident-keep-order` is retired in favour of `deident-US`, which adds the calibrated-ultrasound mask rule to the base profile. Defaults are seeded on first run only — an existing `~/.dicomqr/profiles.json` is never overwritten, so current installations keep their profiles as they are

### Fixed

- **Folder choosers open in front of the application, and where you left off** — the folder dialog is now owned by the window that opened it, so it can never appear behind the application: the previous one was created with no owner window, from a background thread with no right to raise it, and regularly opened underneath. It is also the modern Windows picker — breadcrumb bar, places list, a path you can type into, resizable — and it opens at the folder currently in the field it will fill, rather than wherever Windows last happened to be. Applies to every folder chooser: the Import source, the download folder and default output folder in Preferences, and the Modification dialog's output folder
- **The Import tab has one clearly labelled Browse… button** — it had two folder buttons: Browse…, and a folder icon that opened the source folder in Windows Explorer, which did nothing at all until a folder had been chosen. Since that is the state the tab is always in when first opened, the icon read as a broken control. The two are now a single Browse… button carrying the folder icon; the Explorer shortcut, which duplicated something the picker itself offers, is gone
- **The Import tab remembers the folder you imported from** — the source folder is saved and pre-filled at startup, so importing again from the same disc or department share is a click on Scan rather than a walk back through the file system
- **A second retrieve can no longer start while one is running** — Retrieve Selected (from the button, the Query menu, the context menu, or the retry offer) now refuses with a message while a retrieve is in progress, instead of silently starting a rival run. Two overlapping runs shared the progress bar and status line, orphaned the first run's Cancel, and nested the received-file counting so whichever run finished first disconnected the other's — files could arrive uncounted and unindexed. The guard is released only once the run's completion summary is on screen, so a cancelled run still refuses new work while its in-flight files drain
- **Disconnect now cancels a running retrieve** — it previously stopped the local C-STORE listener but left the retrieve loop issuing C-MOVEs against it, so every remaining sub-operation failed server-side and the run only ended when the stall watchdog gave up two minutes later. Disconnect aborts the retrieve first, and the run reports "Retrieve cancelled" through its normal path
- **The main window reopens on the monitor you left it on** — the saved position was previously clamped into the primary display's work area, so a window parked on a second monitor was yanked back to the first on every launch. The saved position is now judged against the work area of the monitor it actually sits on; a position saved on a display that has since been unplugged resolves to the nearest remaining monitor, so the window is always reachable. The first-run default placement still opens on the primary display

### Removed

- **The UID suffix option** — *Remap UIDs* replaced it in practice: remapping generates fresh, internally consistent UIDs at every nesting depth, where the suffix appended to a UID whose original therefore remained readable inside it. The engine, the profile editor and the Modification dialog no longer offer it. A profile still carrying a `uid` entry — hand-authored or shared from dicomtool — is deliberately **not** stripped: the value survives loading and saving untouched, both editors state that it is there and unusable, and a run of such a profile is refused with a message naming Remap UIDs as the replacement. Silently ignoring the entry would have exported original UIDs from a profile whose author asked for them changed

## [1.13.0] — 2026-08-06

### Added

- **Every modification-profile option is now editable in Preferences** — the profile editor previously exposed only the core fields; the `ignoretype`/`ignoremodality` file filters and the per-modality overrides — both fully honored by the modification engine — appeared only in a "preserved, not editable here" note and could be changed solely by hand-editing profiles.json. The editor now has comma-separated entries for both filters and a per-modality override list with add/edit/delete, each override edited in a nested dialog covering what an override may genuinely vary (see *Modality overrides are scoped to what is genuinely modality-specific*, below) — settings the engine ignores inside an override deliberately have no controls there and round-trip untouched. The editor keeps its single-column layout, with the new controls added as their own sections — tag rules, options, file filters, then per-modality overrides — every field validated by the same rules wherever it appears. Fields the engine never reads (`dicomdir`, `verbose`) still survive a round-trip unchanged, so dicomtool-authored profiles remain safe to edit

- **Date shifting (`shiftdays`), ported from dicomtool v1.5.0** — profiles gain a *Shift dates (days)* option that moves every DA (Date) and DT (DateTime) value by a fixed day offset (negative, zero, or positive), calendar-aware and at any nesting depth, with DT time/fraction/timezone suffixes preserved verbatim. Patient Birth Date is deliberately never shifted — the birth date mask remains that field's dedicated control — and unparsable date values pass through unchanged. The option is editable in the profile editor, per-modality overrides, and the Modification dialog, and its semantics match dicomtool exactly (a hand-authored per-modality override with a garbage value fails that file rather than silently shipping real dates). This also closes a data-loss hole: dicomqr previously did not know the `shiftdays` JSON key, so saving profiles in dicomqr silently stripped it from a profiles.json shared with dicomtool
- **Profiles can default to Zip export** — a profile-level *Zip export* option (new dicomqr-only `zip` key in profiles.json; dicomtool ignores it) pre-checks the Modification dialog's Zip export checkbox, so a profile that always ships archives no longer needs the box ticked by hand every run. The dialog checkbox remains the per-run decision and is never written back to the profile
- **Transfer syntax conversion on export** — a modification profile gains an *Output transfer syntax* option (dicomqr-only `transfersyntax` key, the same `explicit-le`/`implicit-le` tokens the server profiles use): *As stored* copies each file's encoding through untouched, while Explicit or Implicit VR Little Endian convert it, decompressing compressed pixel data on the way out. Until now the only place to force a syntax was the server profile, which converts during the retrieve; converting on export instead keeps the download folder in the archive's own encoding, pays the conversion cost once per export rather than once per retrieve, and turns a file that cannot be converted into one reported failure in an otherwise complete export instead of an object dropped mid-retrieve. Both settings remain available and independent — only the server profile can stop a PACS sending something undecodable in the first place, so requiring nothing there means files the application cannot read (JPEG-LS, RLE, MPEG) can reach the download folder. The option is overridable per run in the Modification dialog, and is profile-wide (never per modality). Only the two uncompressed targets are offered: the application has decoders, never encoders
- **JPEG Lossless files can be exported** — a `.57`/`.70` study, previously displayable in the viewer but impossible to convert, now decompresses during export like JPEG 2000. Retrieve negotiation is deliberately unchanged and still never offers JPEG Lossless, so no server can be induced to send it: decodable does not imply negotiable here

- **Remove tags and Keep tags read as `0008,0080  Institution Name`** — the two lists in the profile editor now show every entry in one consistent form, group and element zero-padded to four digits with the tag's name beside it, matching the tag picker; previously they echoed whatever the profile stored, so the same tag could appear as `8,80`, `0008,0080` or an alias. The name is shown but never stored: saving writes the tag reference alone, in the canonical padded form (see *Tag references are stored in one canonical form*, below). Typing a bare tag number remains valid; it is padded and named next time the profile is opened, and a line that cannot be parsed as a tag at all is stored exactly as typed, so validation reports it rather than it disappearing
- **Pick tags from the DICOM dictionary instead of typing tag numbers** — the Remove tags and Keep tags fields in the profile editor (and in a per-modality override) gain a **Choose…** button opening the whole dictionary as a tree of groups, each opening to its tags with a checkbox. Search matches on tag name, keyword or number — "patient", "0010" and "InstitutionName" all find Patient's Name — and opens the groups containing matches; a Hide retired toggle omits withdrawn tags. The field's current tags open already checked, and since a selection scattered through 5,000-odd tags would be invisible behind collapsed groups, a field that already has entries opens with **Show selected only** ticked so those tags are the list you see; each group header also carries its own tally ("0010  Patient  (72, 3 selected)"). Checkboxes are on individual tags only: the profile format has no group wildcard, so checking a group would expand into hundreds of entries (group 0018 alone holds 895), and removing a whole group is nearly always wrong — group 0028 carries Rows, Columns and Bits Allocated, group 0008 the SOP Instance UIDs. Bulk selection is therefore offered only over an active search. Applying a selection writes every surviving entry in the canonical `GGGG,EEEE` form, spelling included — inheritance no longer depends on how a tag is written — with one exception: a line that cannot be parsed as a tag is kept verbatim so validation can report it. A tag a profile names but the DICOM dictionary does not define has no row to check; it is counted separately and written back untouched

### Changed

- **The main window now reopens where and as you left it** — its position is remembered across sessions alongside its size, which it never was before; a window moved and closed reopens in the same place. On a first run it opens at 60% of the screen width by 80% of its height, centred vertically and left of centre horizontally, leaving the right of the screen clear for a viewer window or another application. Whatever the source, the window is kept wholly within the desktop work area, so it can never be positioned under the taskbar — and a saved position that no longer fits, after a monitor is disconnected or the taskbar moves, is pulled back on screen instead of opening the window out of reach. Fyne cannot position a window at all, so this is done through the Windows API directly, and is a no-op — logged, never fatal — if any part of it is unavailable

- **The tag picker is a window you can move and resize** — opening Choose… beside Remove tags or Keep tags now gives a proper window rather than a fixed panel, so a long selection can be worked through at whatever size suits. The profile editor behind it is dimmed while it is open: the picker copies the field's contents as it opens, so anything typed into that field behind it would be lost on Apply

- **Preferences and the Activity Log are windows you can move and resize** — both were fixed panels pinned to the centre of the application; they are now ordinary windows with title bars. The Activity Log is deliberately left usable alongside the application, so a long log can sit open on a second monitor while you retrieve or push studies, and it now stops its refresh timer however it is closed rather than only via its Close button. Preferences keeps the behaviour it had as a panel — the window behind it is dimmed and inert while it is open, since Apply writes a whole settings snapshot back and changes made underneath it would be discarded. Closing Preferences closes any profile editor opened from it, so nothing is left stranded

- **The profile editor is a window you can move and resize** — Edit Modification Profile opens as a normal window with a title bar rather than a fixed panel pinned to the centre of the application, so it can be dragged aside and made taller to work through a long removal list. Because a window is not modal, editing the same profile twice now raises the window already open instead of starting a second copy that would overwrite the first one's save, and closing Preferences closes any editor still open with it — an editor left behind would have been saving into a list that was no longer going anywhere. Its controls also sit inside a margin matching the Modification dialog's: a window is drawn without the inner padding a dialog gets for free, which left this one's fields running flush to the frame

- **One set value can be defined as a copy of another** — a set value written as `[0010,0010]` takes whatever the same profile sets that tag to, so the profile states the relationship instead of the application inferring it. `base-deident` now ships `0010,0020=[0010,0010]`, restoring the Patient Name → Patient ID link declaratively, and a new `exportname` key does the same for the export folder name. This replaces a link the Modification dialog held as two hardcoded tag numbers, which broke — invisibly, with nothing to inspect — when the Patient Name row was deleted from a profile and re-added. A reference reads only values the profile itself sets, never the value in the file being modified: the latter would copy the real patient name forward into whichever field referenced it, once per file, which is the opposite of what a de-identification profile is for. References do not chain, so cycles are impossible rather than merely detected. **An existing `~/.dicomqr/profiles.json` does not gain these** — seeding never overwrites — so set Patient ID's value to `[0010,0010]` in the editor, or delete the file to re-seed
- **The Modification dialog's Options section matches the profile editor's** — the two now show the same rows in the same order (birth date mask, remap UIDs, remove private tags, shift dates, fix VR, output transfer syntax), built from the same section block, because the two are read against each other and a differing order invites the wrong field being changed. Remap UIDs also shares its row with the UID suffix, greying out while remap is checked; that pairing existed only in the profile editor, and the dialog had the two as separate rows with no link between them, so the exclusion surfaced only as an error on confirm — one the user could not act on. Both now use one implementation rather than two that can drift apart. Zip export is the deliberate exception: in the dialog it sits in the Export section, next to the output folder and export name it changes
- **Set values are listed in group and element order** in the profile editor, matching the Remove and Keep lists; a row whose tag cannot be parsed sorts last rather than disappearing
- **Set values are chosen from the dictionary and checked against the tag's type** — the profile editor's Set values field was a free-text box of `TAG=VALUE` lines; it is now one row per tag, the tag added through the same picker the Remove and Keep lists use and the value in its own field. Values are validated against the tag's DICOM value representation on save: a date field rejects a word, a UID rejects letters, and the string types are held to their length limits. This closes a real hole — the engine only ever type-checked the numeric representations, so setting a date tag to `ANON` was accepted everywhere and wrote a malformed date into every exported file. An empty value still blanks the element, which is what the shipped profile does with Accession Number
- **Tag references are stored in one canonical form, and inheritance no longer depends on spelling** — a profile's Keep list cancels its base profile's Remove list, and that comparison used to be a literal text match: `40,275` in one file and `0040,0275` in the other were different tags as far as the merge was concerned, so a tag the user asked to preserve was silently removed anyway. Tags are now compared by identity rather than spelling, and every reference is stored zero-padded as `GGGG,EEEE`. Any form can still be typed; it is normalised when the profile is saved. The shipped profiles were recoded to the canonical form, with the tag sets verified identical before and after
- **A modification run that had failures now says so in a dialog** — the count was previously a phrase in the progress dialog's status line, easy to close past; a run with any failed file now replaces that dialog with one listing what failed and why (up to twenty by name, the Activity Log holding the rest). A file missing from an export is invisible once the dialog is gone, and a failed transfer syntax conversion means the export is incomplete in a way the user has to know about. Every other file in the run is still exported
- **Modality overrides are scoped to what is genuinely modality-specific** — the per-modality override dialog now offers the modality code, the set/remove/keep tag lists and Keep private tags. Birth date mask, UID suffix, Remove private tags, Shift dates and Fix VR were removed from it: those are profile-wide decisions, set once in the main editor. A hand-authored (or dicomtool-authored) profile that sets one of them inside a per-modality block keeps it — the modification engine still applies it, and the override dialog names it in an italic note so a value with no control is never mistaken for one that was lost
- **Remap UIDs and UID suffix share one profile-editor row** — the UID suffix label and entry now sit directly to the right of the Remap UIDs checkbox and grey out while it is checked, making the mutual exclusion visible instead of a save-time error. Saving with Remap UIDs checked stores an empty suffix (the disabled entry's text is inert); unchecking re-enables the field with the typed value intact
- **The top-level "Keep private tags" checkbox moved to where it works** — the engine honors `keepprivate` only inside a per-modality override, so the top-level checkbox never had any effect. It now appears in the per-modality sub-editor instead; a hand-authored top-level `keepprivate` value is preserved on save and listed in the editor's preserved-fields note

### Fixed

- **A profile that masks a few images no longer decompresses the whole study** — masking requires uncompressed pixels, and the engine decompressed every compressed file as soon as a profile carried any mask region, whether or not the region applied to that file. A study masked on one or two analysis screens was therefore exported in full uncompressed, taking minutes of processing and roughly ten times the disk space — which then had to be read back on re-import. Regions are now resolved against each file's header before any frame is decoded, so files nothing applies to keep their original compression and are copied through as before. On a 177-file echo study, masking one image went from 75 seconds and a 1.4 GB export to 0.1 seconds and 69 MB for the same 25 files; a profile that genuinely masks every image is unchanged, since that work is required

- **Masks drawn in the review window were not applied, and the images vanished from the export** — a region scoped to one image identifies it by SOP Instance UID, but masking is the last step of a run and UID remapping had already replaced that UID by the time the region was matched. The scope therefore matched nothing: rectangles silently did not apply, images marked as needing no masking were not recognised as reviewed, and every ultrasound image with no calibrated region left without an applicable rectangle failed and was left out of the export. Because the shipped base-deident profile remaps UIDs, this affected every run made with it. Masking now resolves against the file's identity as it arrived, captured before anything modifies it, which also covers a profile that removes Modality or the ultrasound region sequence

- **A per-run set value could still violate its tag's type** — the Modification dialog lets every set value be edited for a single run, and that path was the one place the new value-representation check was not applied, so a date field edited to a word in the dialog still reached the exported files. It is now validated there too
- **A crash when the tag dictionary was read while a connection was being made** — the DICOM networking library registers its command-set tags into the same dictionary the application reads, and did so on the first association rather than at startup. Reading that dictionary concurrently — which the new tag picker does — is a fatal error in Go and would have taken the whole application down, so registration now happens once, before anything can read it

### Removed

- **Tag aliases (`tags.json`)** — the alias map let a profile refer to a tag by phrase (`PatientName=ANON`) and predated the tag picker, which now names every tag from the standard DICOM dictionary. Keeping both meant two naming authorities, and renaming an alias silently orphaned every profile that used it. The whole subsystem is gone: nothing reads `~/.dicomqr/tags.json`, it is no longer seeded, and a tag must be written as `GGGG,EEEE`. The shipped profiles were recoded accordingly. **A profile copied from dicomtool that refers to tags by phrase must be recoded before it will run here** — dicomtool retains aliases, so this is a deliberate divergence. An existing tags.json is left on disk rather than deleted, and is simply ignored
- **Mask top pixel rows** — the burned-in-annotation row masking option is removed entirely (profile field, engine, editor and dialog controls) ahead of a planned replacement. This is a deliberate divergence from dicomtool, which retains `maskrows`: a dicomtool-authored `maskrows` value is now ignored by dicomqr and stripped when the profile is next saved from the editor

### Internal

- `transcode.go` — the conversion itself extracted to `convertDatasetSyntax(ds, sourceTS, targetTS)`, which operates on a parsed dataset so both callers share one implementation: `transcodeDICOMFileToTemp` wraps it in file I/O for the receive path (behaviour unchanged, covered by the existing transcode tests), `processFile` calls it directly on the dataset a modification has already transformed. `datasetTransferSyntaxUID` reads (0002,0010) from a dataset, since the modify path never revisits the file. `canDecompressSyntax` gains `.57`/`.70` gated on `jpegLosslessAvailable`; `decompressPixelData` dispatches to a new `jpegLosslessFrameToNative`, which shares `planarSamplesToNative` with `j2kFrameToNative` (the two decoders return identical planar int32 output). `acceptedSyntaxesFor` is deliberately untouched, and `TestAcceptedSyntaxesFor` now asserts JPEG Lossless stays out of it
- `modifyengine.go` — `modifyParams.targetTS`; conversion applied last in `processFile` (decompression rewrites Photometric Interpretation and Planar Configuration and must have the final say over them); `modifyWriteOpts` adds `SkipVRVerification`+`SkipValueTypeVerification` when a conversion is requested, since emitting Explicit VR for elements parsed under Implicit VR would otherwise fail files that write fine untouched; `zipSink.write` takes `[]sdicom.WriteOption` rather than a fixvr mode string. A target syntax counts as actionable in `hasAction`, so a convert-only profile is legal
- `modifyprofile.go` — `TransferSyntax` field, override-wins merge rule, `modProfileTargetSyntax` (an unrecognised token is an error, never a silent "as stored"), and the `tsExportLabel*` constants plus label⇄token mapping shared by both editors. Also `canonicalTagRef`/`normalizeModProfile` (canonicalisation on load, at every depth, keeping unparsable entries verbatim), `tagMatchKey`/`setMatchKey` (the parsed-tag comparison `mergeModProfiles` now uses in all four places it matched strings), and `validateSetValue` with the VR helpers `isDICOMTime`/`isDICOMDateTime`/`isDICOMUID`

## [1.12.0] — 2026-08-03

### Added

- **Ultrasound studies play as chapters, one per clip** — a series holding multi-frame instances now opens in *chapter mode*: one chapter per instance, the frame slider scoped to the chapter on screen, and a **transport bar** beneath it (play/pause, sweep, playback rate, previous/next chapter) over a **filmstrip** of thumbnails, one per chapter, clicked to switch. Previously such a series was flattened onto a single slider spanning every frame in it — the sample echo study was one 5,256-position scrub with no seam between one loop and the next and no way to play any of them. Each chapter keeps its own frame position, rate, sweep setting and running state, so leaving a loop and coming back resumes it where it was. `Space` plays/pauses; `Ctrl+Left`/`Ctrl+Right` step chapters; the wheel and arrow keys move within the chapter as before. A still is a one-frame chapter with its transport disabled rather than a dead button, and a series with no multi-frame instance (CT, MR) is untouched, keeping its existing one-position-per-image slider
- **Cine plays at the rate the clip states** — read from `RecommendedDisplayFrameRate`, `CineRate`, `FrameTime`, `FrameTimeVector` or `ActualFrameDuration`, in that order of preference, and overridable per chapter from the transport. A clip stating none plays at 15 fps. `PreferredPlaybackSequencing` selects sweep (forward then backward) over looping, and `StartTrim`/`StopTrim` bound the loop without hiding frames from the slider. Every value is treated as untrusted: zero, negative and four-digit rates all appear in real files, and each is rejected or clamped rather than being allowed to stall or spin playback. The three rate attributes stored as integer strings are read as such — a decimal-only reader silently skips them in favour of a lower-priority attribute, which reads as "playback is a bit fast" rather than as a bug
- **Chapters are labelled from what the file actually says** — image comments, protocol name or a stated view code where present; failing those, what kind of ultrasound image it is (`2D`, `Colour flow`, `PW Doppler`, and combinations for duplex), derived from the region calibration sequence. Real echo studies routinely carry none of the naming attributes — the sample study has no `ImageComments`, `ProtocolName` or `ViewCodeSequence` on any of its 88 clips — so this is often the only thing distinguishing one clip from another besides its thumbnail. A candidate with no letter in it is skipped as an identifier rather than shown as a name (the echo study writes `0001` in `ImageType`; the SPECT study writes `15003.0.68612207@` in `ProtocolName`)
- **The active clip is buffered so playback runs at its stated rate** — decoding one 1016×758 echo frame costs ~18 ms, leaving a 30 fps clip under two frames of headroom on one core, so playing from disk judders. The chapter on screen is decoded across every core into memory — ~0.3 s for a 53-frame loop — after which playback is a memory read; frames land in order, so a clip can be scrubbed and played before buffering finishes. One clip is held at a time, capped at 384 MB; a clip too large for that loops over the frames that fit and says so in the counter, with the rest still reachable by scrubbing

- **Multi-phase MR series navigate one phase at a time** — a series that covers the same slice stack several times over (in-phase/out-of-phase pairs, diffusion b-values, dynamic timepoints) previously presented as one flat slider: scrolling walked all of phase 1 and then started over at the top of phase 2, and comparing phases at one anatomical position meant scrubbing a full stack-length away and back. Such a series now opens with the slider spanning one phase and a **Phase dropdown** in the bottom bar; switching phases (or pressing **P** to cycle) keeps the slice, zoom, pan and window, so it is a same-slice toggle — the flicker comparison an in/out-phase pair is read with. Detection is structural rather than tag-driven: the instance-ordered slice locations must partition exactly into K ≥ 2 identical runs (stored blocked or interleaved) under one image orientation — chosen because real series defeat any single tag (the sample study's in/out pair is distinguished by `EchoNumbers`, but its diffusion series carries identical echo attributes on both b-values and an empty `DiffusionBValue`). Tags then *name* the phases: echo number/time ("Echo 1 (TE 2.38 ms)"), the vendor sequence name ("ep_b50t" / "ep_b800t"), temporal position, or acquisition number, falling back to ordinals. Anything irregular — mixed orientations (localizers), uneven phases, repeated positions within a run, a bolus-tracking series of many timepoints at one location — keeps today's flat list. Verified against a real abdominal MR study: the 200-file in/out-phase series presents as 2 × 100 with echo labels, the 100-file diffusion series as 2 × 50 with b-value labels, and the ADC and Care Bolus series correctly stay flat

### Fixed

- **Streak artefacts during cine playback on NVIDIA GPUs** — while a clip played (or after hovering the viewer's controls), white glyph-shaped streaks radiated across the *other* dicomqr window, apparently growing from one corner. The cause is NVIDIA's **Threaded Optimization** driver feature, which corrupts multi-window OpenGL rendering: diagnosed with a minimal two-window Fyne app containing no dicomqr code (Fyne 2.7.3, 2.7.4 and 2.8.0 all reproduce; ~170 widgets of any kind in the animating window trigger it within seconds, fewer widgets just take longer; a close-up shows the victim window's own text drawn with garbage geometry — and since the animating window repaints every 33 ms, its own corruption self-heals invisibly, which is why only the quiet window shows damage). No GL error is ever raised, and every application-side counter-measure — shared GL contexts, `glFinish` between windows, unconditional uniform uploads — fails; switching the driver profile's Threaded Optimization off stops it completely (verified on an RTX A6000). dicomqr now writes that profile setting for its own executable automatically at startup through NVAPI's driver-settings API — the same store the NVIDIA Control Panel writes — so no user has to find the switch; the write is checked-not-rewritten on later launches, takes effect at latest from the following launch, and is a silent no-op on non-NVIDIA systems. If the write fails (locked-down driver store), the Activity Log carries the manual instructions
- **Status text no longer perturbs window geometry at display rate** — the frame counter re-labels ~10×/s during playback, and with a proportional font nearly every new number changes the label's width — which changes the window's minimum size, which makes Fyne re-apply the window's size limits, which GLFW implements on Windows as `MoveWindow(..., repaint=TRUE)`: a full repaint of the window frame ten times a second. The counter, the W/L info label and the chapter label are now wrapped in a layout that reports a high-water-mark minimum size, so re-labelling never touches window geometry (the same path fires in earlier releases during window/level drags). Distinct from the NVIDIA artefact above — this one wastes work and can flicker the frame, but was not the source of the streaks

- **Multi-frame files preview every frame, not just the first** — previewing a SPECT reconstruction, projection set or any other multi-frame object showed a single image with the counter reading `1 / 1`: the viewer navigated *files*, and rendered only frame 0 of each. Most modalities store one image per file, so this was invisible on CT and MR, but nuclear medicine stores a whole acquisition in one file — everything after the first frame was unreachable. The viewer now navigates *frames*: each file's frame count is read during the header pass that already orders the series, and every frame becomes a navigable slice, so the counter, slider, wheel and arrow keys span the whole acquisition. The study overview thumbnail for such a series is likewise the middle frame of the acquisition rather than its first. Files are parsed once and cached, so stepping through a multi-frame acquisition decodes one frame per step instead of re-reading the file — a 240-frame projection set scrolls without re-parsing. Verified against a real SPECT/CT study: the 240-frame projection set, the 128- and 87-frame reconstructions, and both 42-frame recons now expose every frame, each decoding to distinct pixel data (the only repeated frames are the genuinely blank slices at the ends of a reconstruction volume)

### Changed

- **Activity Log opens at Errors only and renders instantly at any level** — the dialog now always opens at the Errors only view (problems first, verbosity on demand; the short-lived `logViewLevel` setting is retired — an unknown key in settings.json is ignored, so existing files need no migration). - **Push no longer fails on files with tags newer than the network library's dictionary** — pushing certain studies (first seen: CT with the Multi-energy CT Acquisition Sequence, tag 0018,9362) failed for every file with "body encoder failed", because the C-STORE sender parsed each file and re-encoded it element by element through a library whose data dictionary predates 2018: unknown tags in implicit-VR files were mistyped as UN, and undefined-length UN is unencodable. - **A failing push no longer floods the log with dataset dumps** — each C-STORE encode failure logged the library error verbatim, and that error embeds a multi-line dump of the offending element's entire content (sequence items and all, ~26 lines per file — a failing 857-file push produced ~22,000 lines, drowning the ring). The DICOM parser delivers image frames through a channel with a blocking send per frame *during* the parse, but the viewer only started reading that channel after the parse returned — so any file with more frames than the 8-slot channel buffer deadlocked. CT and MR store one frame per file and never hit this; NM/SPECT stores the entire acquisition as a single file of 40–240 frames (verified against a real SPECT/CT study: the 240-frame projection set and every reconstruction froze; all now load in milliseconds). ### Fixed

- **Closing the application can no longer leave a phantom dicomqr.exe in Task Manager** — closing the window sometimes left the process alive (windowless, still holding the SCP port) after the UI disappeared. An audit ruled out the suspected causes: every termination path (window close, File > Quit, the app-stopped lifecycle hook, the panic safety net) already stops the C-STORE SCP and releases its port via a non-blocking, idempotent `Stop()`, and every file handle in the receive/transcode/export/settings/log paths is closed on all branches (and could not keep a process alive regardless). The actual cause is a race in Fyne 2.7's quit path: the run loop drains its function queue and only afterwards marks it drained, so work posted in that gap — which includes Fyne's own delivery of the OnStopped hook — is stranded with its poster blocked forever; `ShowAndRun` then never returns. Since the app cannot close that window, every termination path now arms a 3-second exit watchdog *after* settings, catalog, and SCP cleanup have finished: a normal shutdown exits before the timer fires, and a wedged one is force-terminated with a log line (`exit watchdog: shutdown wedged`) in dicom.log
- **Collapsing a branch no longer leaves the top of a tree blank** — closing an expanded node low in a scrolled-down tree could leave the rows above it unrendered (sometimes the entire tree area blank) until an unrelated scroll or refresh happened to repair it. Root cause is a virtualization bug in Fyne's tree widget (v2.7.3): it culls rows against its own copy of the scroll offset, synced only by the scroller's scroll callback — but when a collapse shrinks the content, the scroller clamps or resets its offset through paths that never fire that callback, so the tree keeps culling rows that are actually inside the viewport. Every tree in the application (query results, Local Browse, Import, tag viewer) now queues a refresh after each branch close, which re-syncs the offset and redraws the visible rows; the Collapse All buttons, which bypass the per-branch close callback entirely, scroll to the top first (the tag viewer already did this — now shared by all four trees) — the v1.9.0 exe imported `libwinpthread-1.dll` (GCC's threading runtime, dynamically linked by default), so it failed to start on any machine without MSYS2 with "System error: libwinpthread-1.dll not found". Both build scripts now pass `-extldflags=-static`, linking the GCC runtime statically; the exe's only remaining imports are standard Windows system DLLs
- **Preferences Apply can no longer silently zero settings it has no control for** — the Apply handler rebuilt the whole `Settings` value as an explicit field list, so any field missing from that list (as `retrieveStallTimeoutSec` was, resetting hand-tuned values back to the 120 s default on every visit) was silently erased. Apply now copies the current settings and overwrites only the edited fields, eliminating the bug class for all future settings

## [1.8.0] — 2026-07-23

### Changed

- **The transfer syntax requirement is now enforced in the receive path, per file, before it reaches disk** — requiring 'Explicit VR LE' or 'Implicit VR LE' in a server profile guarantees every retrieved file is stored in exactly that syntax. Negotiation (the C-GET proposal list and the C-MOVE storage SCP's accepted presentation-context set) offers the required syntax first — a transcoding-capable server sends it and nothing needs converting — followed by the syntaxes the application can convert locally (the other uncompressed VR, JPEG Baseline/Extended, and JPEG 2000 in openjpeg builds). A file arriving in any non-required accepted syntax is transcoded **while still a temp file**, so the download folder only ever holds conforming files — there is no post-retrieve batch pass, no fire-and-forget goroutine, and no window where a wrong-syntax file exists on disk. A failed conversion fails that C-STORE sub-operation, and any failed sub-operation or target error aborts the whole retrieve with a dialog reporting the required syntax, the failure details, and how many (all-conforming) files arrived before the abort. The completion status reports how many files needed local conversion, making a non-transcoding server visible at a glance. This replaces v1.7.0's 'preferred' negotiation and its post-retrieve 'Guarantee uncompressed on disk' pass, which could silently leave a study as a mix of syntaxes (observed 2026-07-23: ~half a study left as JPEG 2000 despite the guarantee, and study- vs series-level retrieves gave differing results)
- **'Guarantee uncompressed on disk' checkbox removed** — conversion is now intrinsic to requiring a syntax. The `ensureUncompressed` settings field is ignored on load; the pre-v1.7 `transferUncompressed` flag now migrates to `transferSyntax: "explicit-le"` alone
- **Re-retrieves replace syntax-mismatched copies** — with a required syntax set, an existing on-disk file whose transfer syntax differs from the requirement is replaced by the incoming (converted-if-needed) copy; matching or unrestricted files are skipped silently as before

### Fixed

- **`dicom.log` and the Activity Log were always empty in release builds** — the log output went through `io.MultiWriter(os.Stderr, file, ring)`, and in a `-H windowsgui` build launched from Explorer, `os.Stderr` is an invalid handle whose writes fail; `io.MultiWriter` stops at the first failing writer, so nothing ever reached the log file or the Activity Log dialog. Every sink is now wrapped in a failsafe writer (file first), verified end-to-end against a detached GUI launch. Each session starts with a version/build header line, and two previous sessions are kept (`dicom.log.1`, `dicom.log.2`) so evidence of a hang survives restarts
- **`dicom.log` no longer goes silent after the session-start line** — even with the failsafe writers, real sessions were observed (2026-07-23) whose log files contained only the header: every later write to the session's long-lived file handle vanished without an error surfacing, which destroyed the evidence needed to diagnose that day's transfer-syntax incident. The file sink no longer holds a handle at all — it reopens the log in append mode for every write, so nothing that invalidates a previous handle (a second instance's log rotation, antivirus interference, a recreated directory) can kill file logging for the rest of a session; write failures are counted and the first is reported to the Activity Log ring. The ring and stderr sinks are also now wired even when the home directory is unavailable (previously the whole redirect was skipped and windowsgui builds lost all logging). Sessions additionally log their starting configuration (profile count, download folder, AE title, SCP port), each retrieve's method and required transfer syntax, and every settings save — so a log file alone can reconstruct what the app was configured to do
- **Settings saves no longer fail silently** — `saveSettings` returned on any error without a trace, so a failed write left `settings.json` stale while the app behaved as configured (observed 2026-07-23: mid-session preference changes that never persisted). The atomic-rename step is now retried (3 × 150 ms) to ride out antivirus/indexer holds on the destination, every save logs its outcome, and a save failure from the Preferences dialog shows an error dialog stating that the settings apply to this session only
- **Negotiation visibility** — the log now records, for every association in both directions, each presentation context's offered transfer syntaxes and the chosen one, rejections with the local accepted set (always logged), and the storage SCP's active transfer policy per incoming association — enough to diagnose transfer-syntax negotiation problems from the log alone

- **C-GET retrieves of whole studies (≥124 instances) no longer wedge partway through** — the DIMSE dispatcher kept locally-initiated commands and peer-initiated commands in one map keyed by message ID alone. Our C-GET command takes message ID 124, and the PACS numbers its C-STORE sub-operations from 1 upward — so the 124th instance of a retrieve collided with the C-GET command itself and was mis-routed to the C-GET response loop instead of the C-STORE handler, stalling the transfer. Series-level retrieves stayed under the threshold, which is why only study/patient selections failed. Message IDs are scoped to the initiating AE (PS3.7), so the dispatcher now keeps peer-initiated commands in their own keyspace; responses route only to local commands, requests only to peer commands
- **C-GET received files were stamped with the wrong transfer syntax** — every file received over C-GET was labelled with the *query context's* negotiated transfer syntax instead of the storage context the instance actually arrived on. Harmless while both were uncompressed variants, but corrupting once storage contexts can negotiate JPEG 2000 (v1.7.0 preference fallback): a JPEG 2000 payload would be saved with meta claiming Explicit VR LE. The C-STORE handler now takes the transfer syntax from its own sub-operation's presentation context
- **C-GET parity fixes** — final status 0xBxxx (sub-operations complete with failures) is now treated as a completed transfer with a logged warning, matching the C-MOVE behaviour, instead of failing the whole retrieve; a peer request with no registered handler is logged and dropped instead of crashing the process by invoking a nil callback
- **Retrieves no longer hang forever on non-image series (SR, Presentation State, encapsulated PDF)** — some PACS C-MOVE agents stall while sending objects that carry no pixel data: the association stays open but no further data or progress response ever arrives, and the retrieve previously hung until the application was killed. A stall watchdog now aborts the retrieve after 120 seconds of total silence (no C-MOVE-RSP, no received file) with a status message and a dialog explaining the likely cause and recommending Retrieve method C-GET or Auto for the affected server. The timeout is configurable via `retrieveStallTimeoutSec` in settings.json (-1 disables it, for slow tape archives)
- **Cancelled and stalled retrieves now tear the association down** — cancelling a retrieve (or a watchdog abort) previously left the DIMSE goroutine blocked forever and the TCP association open; it now sends A-ABORT, unblocks the pending operation, and reaps the goroutine. Applies to C-MOVE, C-GET, and Push to PACS

## [1.2.0] — 2026-06-17

### Added

- **Request uncompressed transfer syntax** — each server profile now has a "Request uncompressed transfer syntax only" checkbox in the profile editor. When enabled, dicomqr restricts the A-ASSOCIATE-RQ presentation contexts to Explicit VR Little Endian and Implicit VR Little Endian only, causing a conformant PACS to transcode compressed pixel data before delivery. Applies to both C-GET (SCU transfer syntax list) and C-MOVE (embedded C-STORE SCP rejects compressed syntaxes at association time with `PresentationContextProviderRejectionTransferSyntaxNotSupported`).

### Fixed

- **Image viewer: compressed pixel data error** — files using JPEG 2000 (Lossless/Lossy), JPEG-LS (Lossless/Near-Lossless), JPEG Lossless Non-Hierarchical, or RLE Lossless transfer syntaxes now display a clear, actionable message ("use Open in Viewer") instead of the cryptic "Invalid JPEG Format: missing SOI marker" error that appeared because the suyashkumar/dicom library unconditionally passes all encapsulated frames to `jpeg.Decode`
- **Image viewer: undefined-length uncompressed pixel data** — DICOM files from certain vendors that store uncompressed pixel data with an undefined-length VL are now decoded correctly. The suyashkumar/dicom library previously treated undefined-length pixel data as encapsulated (JPEG), causing the same JPEG decode failure on some systems. A raw-pixel fallback path now reinterprets the bytes natively using the image dimensions, bit depth, rescale parameters, and photometric interpretation from the dataset; this was the root cause of the "same data works on one system but not another" behaviour

### Internal

- Vendored `thirdparty/go-netdicom` extended: `ServiceProviderParams.AcceptedTransferSyntaxes []string` — when non-empty, the service provider selects only offered transfer syntaxes that appear in the list during A-ASSOCIATE-RQ negotiation, rejecting contexts where none match; `contextmanager.go` patched to iterate all offered syntaxes rather than blindly picking the first
- `viewer.go` — `unsupportedTransferSyntaxNames` map for proactive transfer syntax detection; `renderRawPixelFallback` for native pixel decode of misidentified encapsulated frames; `dicomIntParam` helper for integer dataset lookup

## [1.0.0] — 2026-06-03

Initial public release.

### Added
- **Per-profile retrieve method** — each server profile has a **Retrieve method** setting (C-MOVE / C-GET / Auto), configurable in **File > Preferences… > Connections > Edit**
- **C-GET retrieval** — C-GET transfers files back over the same association; no inbound C-STORE SCP port or PACS-side registration of a destination AE is required
- **Auto mode** — attempts C-GET first; falls back to C-MOVE automatically if the PACS rejects or does not support C-GET
- **Export results** — Query menu → **Export…** saves the current results tree to CSV or JSON; studies with no series loaded produce one row each, studies with series loaded produce one row per series
- **Series-level query and retrieve** — expanding a study fires a SERIES-level C-FIND and lets individual series be selected and retrieved
- **Multi-select modality filter** — modalities are ticked via checkboxes and each is dispatched as a concurrent single-modality C-FIND, merged and deduplicated client-side
- **Automatic wildcard search** — Patient Name, Patient ID, and Accession Number fields automatically append `*` on search when the value does not already end with one
- **Results tree sorting** — patients alphabetical by name; studies chronological by date; series numeric by series number
- **Select All / Clear Selection** — buttons in the retrieve panel; **Esc** also clears the current selection
- **Expand All / Collapse All** — buttons above the results tree
- **Customisable selection appearance** — **Preferences → UI** sets the colour and font style (bold / italic) applied to selected tree rows; an unset colour follows the theme's primary colour
- **Connect timeout** — per-profile **Connect timeout (s)** field (default 10 s) prevents indefinite hangs on unreachable servers
- **Cancel connect** — the **Disconnect** button becomes **Cancel** while connecting and aborts the in-flight C-ECHO
- **Retry failed retrieve targets** — after a partial retrieve a dialog offers to retry only the failed targets
- **Profile reordering** — Up/Down buttons in the Connections preference list reorder server profiles
- **Ctrl+R shortcut** — triggers Retrieve Selected (mirrors the menu item)
- **Progress reporting** — an indeterminate progress bar animates during C-FIND; the retrieve bar advances per target so C-GET (which carries no sub-operation count) also shows progress
- **Live loading count** — large result sets are inserted in batches across UI frames with a `Loading results… N/total` counter, keeping the window responsive
- **Window size persistence** — the window size is saved on exit and restored on the next launch
- **Download directory default** — defaults to `~/DICOM Downloads` when none is configured
- **App icon** — embedded in the Windows executable and shown in the **Help > About** dialog and the user manual title page
- **Filter debounce** — the results filter waits 150 ms after the last keystroke before re-running
- **Air-gapped IP detection** — `localIP()` enumerates network interfaces when the UDP probe to `8.8.8.8` fails
- **Inline server profile validation** — AE Title (required, ≤ 16 chars) and Port (1–65535) are validated in the server editor

### Changed
- **Results tree selection behaviour** — parent/child-aware: selecting a node selects all its loaded descendants; narrowing and per-child deselection behave intuitively; expanding a selected node auto-selects newly loaded children
- **Filter popup** — the Filters dropdown is a modal popup that auto-dismisses on outside click
- Results tree starts fully collapsed after each search; expanding a study triggers the series C-FIND

### Fixed
- **SCP port left locked on exit** — closing the window (X), File → Quit, and any other termination route now stop the embedded C-STORE listener and release its port; previously only the Disconnect button did, so the port could stay bound after the app closed and block a restart. `StorageSCP.Stop()` now closes the listener synchronously, and an app-stopped lifecycle hook acts as a final safety net. If the port is still in use when connecting (e.g. after an unclean kill that bypasses shutdown), the SCP retries the bind briefly and then reports a clear, actionable message ("port N is already in use — another copy of dicomqr may still be running…") in a dialog rather than a raw socket error
- **Connection-state data races** — the active client, C-STORE SCP, query context, and active profile are now guarded by a mutex, removing the race (and possible nil-deref) between disconnect on the UI goroutine and an in-flight retrieve
- **Download directory validated up front** — a retrieve now fails fast with a clear message if the download folder cannot be written, rather than erroring per received file
- **Filters popup validation error** — re-opening the Filters panel after a search no longer shows a spurious date-parse error on empty date fields
- **Cancel retrieve** — pressing Cancel reliably shows "Retrieve cancelled"; the C-STORE and C-GET callbacks check `ctx.Err()` before posting UI updates
- **Error 45056 (C-MOVE warning) recovery** — DICOM warning status 0xB000 is no longer treated as fatal; multi-series retrieves continue and the final status reports warning counts
- **Path-length guard** — each folder component is truncated to 64 characters; the path falls back to a flat `<downloadDir>/<sopInstanceUID>.dcm` layout when it would exceed 255 characters
- **Windows reserved device names** — path components matching `CON`, `NUL`, `PRN`, `AUX`, `COM1`–`COM9`, `LPT1`–`LPT9` are prefixed with `_`

### Internal
- Data-race fixes for `state`, `StorageSCP.downloadDir`, and `scp.OnFileReceived` (mutex-guarded)
- Atomic settings write (temp-file + `os.Rename`) to prevent settings corruption on crash
- `sort.Search`-based sorted insert replaces `sort.Slice`-on-every-insert (O(N log N) vs O(N² log N))
- `applyFilter` deferred out of the per-insert path — called once per batch
- `tree.RefreshItem(id)` replaces full `tree.Refresh()` after series lazy-load
