# Changelog

## [Unreleased]

### Added

- **Parallel transfers: a retrieve can fetch several studies or series at once.** Each server profile has a new *Parallel transfers* setting, 1 (the default, unchanged behaviour) to 4. With more than one, a retrieve of several studies or series shares them across that many connections to the server, which helps most when the server is slow to answer each request. DICOM offers no way to ask a server how many connections it allows, so the setting is opt-in. A **Test** button beside it opens that many connections together and reports, for each one, whether the server accepted it or refused it and why (for example "local limit exceeded"). Test cannot show that retrieves will get faster, since some servers accept several connections and still send C-MOVE deliveries one at a time, and the profile window says so. If, during a retrieve, the server refuses an extra connection, or one fails or every open one stops responding, the retrieve carries on one connection at a time: the studies or series affected are fetched again, nothing is lost, and the completion status says the server would not take parallel transfers and why. Works with C-MOVE, C-GET and Auto alike.
- **A refused connection now says why.** When a server rejects a connection outright, the Activity Log names its reason ("local limit exceeded", "called AE title not recognized", and so on). Previously it reported only "Connection failed", and the rejection reason it logged could be misnamed: the same reason code means different things depending on which part of the server sent it.

- **The PHI check now looks at text fields too.** Beyond images and documents, it lists free-text and identifying fields that carry a value and that the profile neither removes nor replaces: the comment fields (Image, Patient, Study, Visit and Identifying Comments, Additional Patient History, the requested-procedure, imaging-request and performed-procedure-step comments, and report text) and the demographics beyond name, ID and birth date (Other Patient IDs and Names, birth and mother's birth names, address, telephone and telecom details, medical record locator, admission ID). The list follows the fields the DICOM standard's basic confidentiality profile removes; name, ID and birth date are left out because every profile deals with them, and study, series and protocol descriptions because they carry names too rarely to flag every file. Fields are found wherever they sit, including inside request sequences, and per-modality overrides are taken into account exactly as the run applies them. The finding names each field with the number of files carrying it, and **Remove these fields in this run** adds them to the run's removals (shown in the Tags removed list; the profile itself is unchanged). The completion summary counts exported files that still carried such a value, and the Activity Log names the fields for each one. With the shipped base-deident profile, which already removes most of these, the check surfaces the four it does not: the retired Identifying Comments and Study Comments, Requested Procedure Comments, and Comments on the Performed Procedure Step.

### Changed

- **A server profile is edited in its own window.** Edit or Add server… in Preferences now opens a window that can be moved and resized, like the modification profile editor, instead of a fixed dialog. A failed check (an empty AE title, an out-of-range port) no longer closes it and throws away what was typed.
- **A retrieve waits for each connection to close before opening the next.** It used to start the next study's connection while the previous one was still closing, briefly holding one more connection than intended. A server that strictly limits connections per AE could refuse that one.
- **Buttons look like buttons.** Ordinary buttons — Review masking…, Browse…, Change…, the PHI check's remedies, and every other button that is not a window's main action — were filled with a shade barely different from the window background (in the default light theme, a very pale grey on white), so they were hard to tell from bold labels. Their fill is now a clearly visible step darker (or, in dark themes, lighter) than the background, in every window and every colour theme, with the button's text still easily readable on it. Main-action buttons such as Modify… keep their accent colour.

### Fixed

- **Applying Preferences during a retrieve no longer changes it partway through.** A running retrieve read the local AE title (the C-MOVE destination), the C-GET save folder and the stall timeout from the live settings each time it needed them, so pressing Apply mid-run could change them between one study and the next. It now keeps the values it started with, and the next retrieve picks up the change.

## [1.22.0] — 2026-09-30

### Added

- **The Modification window checks a run for PHI its profile would not reach.** As the window opens, a new *PHI check* section reads the header of every file the run will export — in the background, never holding up Modify… — and lists what the profile's tag rules and pixel masking would leave untouched:
  - images that declare burned-in annotation (Burned In Annotation = YES) with no mask covering them;
  - encapsulated documents (PDF, CDA, STL) — the document inside travels as it arrived, since no tag rule or mask reaches into it;
  - ultrasound images with no mask, whose screens nearly always carry a banner with the patient's name;
  - screen captures and colour images filed under a greyscale modality (CT, MR, NM, PT and others) with no mask — the shape dose pages, scanned forms, saved screens and 3D renders take;
  - overlay planes kept while Remove overlay planes is off.

  Each finding offers its remedy: *Review the N flagged image(s) in masking…* opens the review window on just those images, *Leave these files out of this run* drops the flagged documents, and *Remove overlay planes* ticks that option. The list updates as masking is reviewed or options change. It honours the profile's own filters, so a file the run would skip is never flagged. Modify… asks for one confirmation only when a file declares burned-in text or an embedded document is still included; the other findings stay advisory. After the run, the completion summary states how many exported files still carried each kind — counted from the files as written, so it reports what the export holds whether or not the check had finished. The check reads headers only: it cannot see text burned into an ordinary greyscale image, so finding nothing is not proof an export is clean.

### Changed

- **Retrieves that convert files no longer hold up the PACS.** When a server profile requires a transfer syntax and the PACS sends files in another one, each file used to be converted before the PACS was told it had arrived — and the PACS waits for that answer before sending the next file, so the whole transfer ran at the speed of one decoder. Files are now acknowledged as soon as they arrive and converted in the background, several at a time on the same resource limits as a modification export (about one per physical core, below-normal priority, within the memory limit), with large multi-frame files spread across idle cores. Measured on 20 multi-frame JPEG 2000 objects: the PACS finished sending after 0.25 s instead of 6.6 s, and every file was converted and saved after 3.1 s instead of 6.6 s. The retrieve waits for the last conversions before reporting ("Converting N received file(s) to …"), so every file is counted and appears in Local Browse. Files that need no conversion are handled exactly as before.
  - One consequence, chosen deliberately: a converted file that then cannot be saved — a folder that cannot be created, say — can no longer be reported to the PACS as a failure, since it was already told the file arrived. It is reported locally instead, in the Activity Log and as "N received file(s) could not be saved after conversion" in the retrieve's summary.
  - If dicomqr is closed, or stops, while conversions are still running, nothing is lost: the received files wait in the download folder under names that record the syntax they need, and are converted, filed and indexed the next time dicomqr starts.
- **JPEG images display about three times faster.** The viewer now decodes JPEG Baseline images — echo studies, most notably — with libjpeg-turbo, which is already part of the release build, instead of Go's slower decoder: measured on a real echo clip, 5.4 ms a frame instead of 16.2, so clips buffer for playback that much sooner. Filmstrip and study-preview thumbnails decode only at the size they are shown (2.2 ms a frame). This applies to what is shown on screen only; de-identification exports keep their existing decoder, so exported pixels are unchanged. Colour images of every kind are also converted for display once, when decoded, rather than on every pan, zoom or resize.
- **Pushing to a PACS starts sooner and reads each file once.** A push used to check every file one at a time before connecting — on a cold mechanical drive, around a minute and a half of apparent inactivity for 10,000 files — and then opened each file twice more to send it. The check now reads several files at once, its results are reused for sending, and each file is read from disk while the previous one is still being sent.
- **Searching in the tag viewer and tag picker stays responsive.** With a search active, the tag viewer re-checked its entire tree — lowercasing every label — each time it redrew, which on a large study made scrolling crawl; it now works out what matches once per search. The tag picker's search waits until typing pauses, like the other filters, and no longer rebuilds its search text for 5,000 dictionary entries on every keystroke.
- **Local Browse checks, deletes and reloads faster.** Checking whether a touched patient's or study's files are still on disk now reads each folder once instead of each file (a patient of 20,000 files is a few dozen folder reads), and is not repeated for the same item within 30 seconds; it also no longer treats a folder it merely could not read, such as one on a drive that has gone to sleep, as deleted. The Delete dialog opens at once and fills in the total size when it is known, instead of freezing the window while every file was measured first. Reloading the index after a retrieve or import skips a redundant pass over every file.
- **Smaller improvements.** The viewer keeps its drawing buffer between slices instead of reallocating it on every step, and a newly selected cine clip's file is read once rather than twice. Modification exports reuse their read and write buffers instead of allocating fresh ones for every file. Network packets are encoded without an extra copy of the data. dicomqr's start-up no longer waits for the NVIDIA driver-profile check before building its window (about a quarter of a second).
- **Received data no longer goes through temporary files.** Every query result and every received image was first written to a temporary file in the Windows temp folder — the file reopened for every network packet — and each image then copied again into the download folder. Each message is now held in memory up to 8 MB, which covers every query result and ordinary CT, MR and nuclear medicine images; only larger objects (radiographs, multi-frame acquisitions) still use a temporary file, now kept open while it fills rather than reopened packet by packet. Memory use stays bounded however many transfers run at once.

## [1.21.0] — 2026-09-29

### Added

- **Modification profiles can skip files by SOP Class** — a new *Ignore SOP classes* filter (profile field `ignoresopclass`, a comma-separated list of SOP Class UIDs) skips any file whose SOP Class UID (0008,0016) matches, beside the existing Image Type and Modality filters. It exists for the series that sit inside a study looking like part of the imaging but are scanned documents, dose and protocol pages or saved screens: those arrive as Secondary Capture objects labelled with the study's own modality (CT, MR, NM, PT), so neither existing filter could catch them. A survey of 55,920 downloaded files across 25 patients found every such series to be Secondary Capture, found no natively classed image series that looked like a document, and found one scanned form with no Image Type at all — which is why the filter keys on the SOP class rather than on Image Type SECONDARY (that would also drop MPR reformats). Known classes are named beneath the field as they are typed, and an entry that is not a UID is refused rather than left to match nothing. The filter is also honoured inside a per-modality override, where it adds to the profile's list for that modality alone, so a base profile can skip Secondary Capture for CT, MR, NM and PT while an echo study's measurement screens (Secondary Capture too) stay for pixel masking. dicomqr-only; dicomtool ignores the field.

- **Modify Selected… de-identifies just the selected series** — a new Local Browse button beside Push Selected… and Delete Selected… runs a modification profile over exactly what is selected, instead of the whole patient or study the right-click Modification submenu always takes. Select the series to export (Ctrl+click, Shift+click), click Modify Selected…, pick the profile from the menu that opens, and the usual Modification window opens with a header saying how much is included ("3 of 7 series selected"). Series from one study make a study-level run, exported exactly as a right-click on that study would be, just with fewer series; a selection across several studies of one patient makes a patient-level run. A selection spanning more than one patient is refused with an explanation: an export stands in for one patient under one export folder name, and the profile's set values — a new Patient Name, and the Patient ID following it — would give every patient in it the same identity.

### Changed

- **Selecting in the Query Results, Local Browse and Import trees now follows the Windows convention**: a plain click selects that row and deselects everything else, Ctrl+click adds or removes a single row, Shift+click selects the range from the last click in place of the current selection, and Ctrl+Shift+click adds that range to it. Previously every click toggled its row in or out while leaving the rest of the selection alone, so a row clicked earlier and forgotten stayed selected and was quietly included in the next Retrieve, Push, Delete or Import; selecting several rows now always takes a deliberate modifier. Clicking the row that is the only selection deselects it (a selected study counts as one row together with its series), so a lone selection no longer needs Clear Selection to drop; with several rows selected, clicking one of them keeps just that one. Ctrl+click still removes a single row from a larger selection, including one series out of a selected study, which narrows the study as before. The arrow beside a patient or study only opens or closes it and never changes the selection. Shift ranges still run only between siblings (series of one study, studies of one patient); a Shift+click anywhere else selects just the row clicked.

- **Modification runs that do not mask pixels are far faster.** A profile that only changes tags (set values, removals, UID remapping, date shifting, a transfer syntax conversion) used to unpack every uncompressed image into individual samples on the way in and pack it again on the way out, which was most of the work for a CT or MR study. The pixel data is now copied through as the bytes it was stored as: measured on a 512×512 slice, 25 ms of processing became under half a millisecond, and the exported pixel data is byte-for-byte identical to the source. Runs that mask are unchanged, since masking has to work on the samples themselves.
- **Opening images reads only what it needs from each file.** Several places that needed only a file's header information — preparing a series or study preview, opening the Review masking window, sizing each file before a masking or conversion run, and naming files during an import — read every file to the end to get it, image data included, so the wait grew with the size of the study rather than the number of files. They now stop before the image data, the same technique the folder scan has used since 1.17.0, and the previews and the Review masking window read several files at once. (Import still copies one file at a time on purpose: its source is often a CD or USB stick, where reading several at once is slower.) A masking or conversion run in particular used to read every file in full twice. The study preview also no longer multiplies its disk reads by the number of series: it used to start every series at once, each reading several files in parallel and decoding its own preview image, so a study with dozens of series put hundreds of reads in flight together — slower, not faster, on a mechanical drive. It now reads every series' headers through one shared set of readers, then decodes at most four preview images at a time. Indexing new files after a retrieve or an import also reads several files at once now, rather than one at a time.
- **Selecting many rows no longer freezes the tree.** Select All, or Ctrl+clicking a patient with many series, used to repaint the tree once per row it selected, each time redoing the layout of every open row, so a large selection in an expanded or filtered tree could hang the window for seconds. Each click now repaints the tree once.
- **The protocol log no longer slows transfers down.** `dicom.log` recorded roughly five lines for every network packet exchanged with a PACS — each packet sent or received and each step of the connection's internal state — and wrote each line to disk separately, reopening the file every time while every other part of the application waiting to log queued behind it. A large retrieve or push was held back by its own logging, and the flood also pushed genuine warnings and errors out of the Activity Log. The per-packet trace is now off by default; associations and every DICOM message are still recorded, which is what diagnosing a PACS problem needs, and setting the environment variable `DICOMQR_DICOMLOG_LEVEL=3` brings the packet trace back for a protocol investigation. Log lines are also written in small batches (at most a fifth of a second behind), except errors, which are written immediately along with everything before them, so the lines explaining a failure are on disk even if the application then stops.
- **Several smaller speed-ups.** A received file that has to be converted to the required transfer syntax is written in large blocks instead of many small ones, shortening the time the PACS waits between objects. Masked exports of JPEG-compressed colour images (echo studies) convert each decoded frame to RGB about four times faster. Adding files to the Local Browse index after a retrieve, import or scan takes about a quarter of the time it did (measured: 10,000 files in 94 ms instead of 355 ms).
- **Zip exports compress on every worker instead of one.** Compressing each file into the archive happened inside the step that adds it, which only one file can do at a time — so however many files were being modified in parallel, a zip export compressed them one after another on a single core, and the others waited. Each file is now compressed as soon as it is ready, alongside the rest, and only the finished bytes are added in turn: measured on 120 uncompressed CT slices, 0.7 s instead of 1.8 s. Images whose pixel data is already compressed (JPEG, JPEG 2000) are now stored in the archive as they are rather than compressed a second time, which saved almost nothing and cost a full pass over every byte. The archive's contents are unchanged, file for file.
- **Modification exports size themselves to the machine and yield to everything else.** An export used to process four files at once on any computer — every core of a four-thread laptop, so the machine crawled until it finished, but only a quarter of a large workstation. Exports that are heavy on the processor (zip archives, pixel masking, transfer syntax conversion) now use about one worker per physical core, between two and eight, leaving the rest free; plain tag-only exports, which mostly wait on the disk, keep the four they had (fewer on a machine with fewer processors). The export's workers also run at below-normal priority, so on an idle machine they go full speed, but the moment you — or another application — need the processor, you get it first. A cap on memory that until now applied only to exports that decompress images now applies to every export, so a run meeting a handful of very large files processes them fewer at a time instead of holding them all in memory at once. `DICOMQR_MODIFY_WORKERS` sets the number of workers explicitly, for trying a different number on a particular machine.
- **Large multi-frame images mask and convert several times faster.** A multi-frame file — a SPECT acquisition, a long echo clip — was decompressed, and after masking re-compressed and checked, one frame after another on a single worker. Because such a file is also the one the memory limit holds back until the rest are done, it tended to be the last thing left, running alone on one core while the others sat idle. Its frames are now spread across whichever of the export's workers are free: measured on a 40-frame 512×512 JPEG 2000 file, 0.7 s instead of 2.4 s. This never uses more of the machine than the export already may, only cores the export has finished with, and every re-compressed frame is still decoded again and compared before it is written.
- **Scrolling through a series in the viewer keeps up.** Slices you have already seen stay decoded, the viewer reads ahead a few slices in the direction you are scrolling, and flipping between MR phases (P) shows the other phase at once because it has already been read. A fast scroll no longer decodes every slice it passes on the way — only the one the slider stops on.
- **JPEG 2000 images display faster.** The image you are waiting on is now decoded on all processor cores rather than one (measured about 2–3× faster, more on larger images), and thumbnails — the viewer's filmstrip and the study preview — decode only the resolution they are shown at, which JPEG 2000 files store separately: a 2048×2048 image's thumbnail took 10 ms instead of 204 ms.
- **Window/level adjustment is faster, and greyscale images need half the memory.** Dragging the window recomputed every pixel from scratch; it now builds a table of the few thousand possible values once per change and looks each pixel up — about three times faster (a 3000×3000 radiograph re-windows in 12 ms rather than 48 ms), with identical results. Images that carry no window settings, common for ultrasound, nuclear medicine and some radiographs, choose their initial window from a histogram instead of sorting every pixel, which on a 3000×3000 image took over half a second and now takes 7 ms. Greyscale frames are held in half the memory they were, so the clip buffer fits twice as many frames of an XA or SPECT clip in the same space.
- **Retrieve, Modification and Import progress no longer floods the window.** The retrieve status line used to be rewritten for every file received, and the Modification and Import progress every ten files, however fast they arrived; each rewrite of a line whose length changes repaints the whole window, so a fast transfer kept the window busy repainting. Progress is now shown ten times a second at most, whatever the rate.

### Fixed

- **A fast scroll through a series can no longer come to rest on the wrong slice.** Each step of the slider or mouse wheel started its own decode, and they could finish in any order, so the image shown after a quick scroll was sometimes a slice the viewer had passed rather than the one the slider and counter showed. Only the slice the slider stops on is now shown.
- **Zooming into an image in the viewer no longer distorts it.** Any zoom above fit showed the image sheared — each row drawn further to one side than the last — because the zoomed area was handed to the display still laid out as part of the full image, and the display read its rows as if they followed one another directly. The zoomed area is now copied out on its own before it is shown, so panning and window/level adjustment while zoomed display exactly the pixels they should.
- **An unusual file can no longer close the application when it is imported or viewed.** Reading a file's naming tags during Import, and reading an image's details in the viewer — the patient and study text on the image, its window/level, rescale, bit depth and colour type — could crash the whole application on a tag stored with an unexpected data type, and in the viewer this happened in the background as images were preloaded. Such a value is now treated as missing, and the image falls back to its defaults; a whole number stored as text is now read correctly. A file whose pixel description itself is unreadable still cannot be displayed, but reports that instead of crashing.

## [1.20.0] — 2026-09-02

### Added

- **Series within a study can be range-selected with shift-click**, in Local Browse, Import and the Query Results tree alike: click one series, then shift-click another, and everything between them is selected — the fast way to pick several series out of a large study without clicking each one individually. The range is added to whatever else is already selected; nothing outside it is touched, and a shift-click that doesn't land on a sibling of the last plain click (a different study, or nothing clicked yet) just selects that one item instead of guessing at a range.

- **The Review masking window now finds the problems instead of making you scrub for them.** A "Next failure" button jumps straight to the next image that cannot be masked and would fail the export — in whatever series it sits, wrapping past the end of the run — with a live count that reaching zero means the run exports clean; on a plain slice stack, which gets no filmstrip, this is the only flag a failing image gets. A counts line beside the image position tallies the whole run by outcome (masked / fallback / exempt / fail / untouched) in the same colours the filmstrip stripes use, updated as regions are drawn and undone, so it doubles as the colour legend. Navigation is labelled for what it does — "< Series / Series >" step series, new "<" and ">" beside the slider step single images — and the paragraph of instructions at the top is cut to two sentences, since the window now explains itself where each thing happens. Cancel and the title-bar X ask before discarding a session's drawn regions, and dragging on the image with Draw rectangles unticked says why nothing is happening instead of doing nothing silently.

### Changed

- **A rectangle drawn in the Review masking window and set to reach beyond the one image now stops at the series it was drawn in, and — for a series with separate chapters to review, such as an ultrasound series mixing clips and stills — at the one chapter**, instead of reaching into every other series (and study) the run happened to include, or every other clip of the same series. The "Images of this size" option becomes "Current chapter" or "Current series", showing whichever applies to the series being reviewed: for a series with no separate chapters (a plain slice stack, most CT and MR series) it reaches every like image across that whole series, since there a repeating layout is a statement about the acquisition as a whole; for a series that does have them, it stays confined to the one chapter drawn on, since a rectangle drawn on one clip is not a statement about a different view that happens to share its geometry. The match against modality, pixel dimensions and (for ultrasound) calibrated-region state is unchanged, so a differently laid-out worksheet mixed into a chapterless series is still left alone.

### Fixed

- **Deselecting one series of an already-selected study no longer leaves the whole study selected.** Selecting a study (or a patient) fans the selection out to every series beneath it, but in Local Browse and the Import tab, clicking a series back off only cleared that one series — the study itself stayed flagged selected, so Push Selected, Delete Selected and Import Selected kept operating on every series underneath it, including the one just excluded. Deselecting a series now clears the stale flag on the study (and patient) above it too, the way the Query Results tree's own selection already worked.

- **Scrollbars inside scrolling dialogs no longer sit in each other's grab zones.** A list or multi-line field that scrolls on its own — the profile lists in Preferences' tabs, the Tags removed list in the Modification dialog, the Remove/Keep tag fields in the profile editor and its per-modality override — used to end flush against (or within a few pixels of) the dialog's own scrollbar, so dragging one bar routinely caught the other. Such content now keeps a clear gutter, the width of a scrollbar plus a little air, between its right edge and the dialog's, so each bar is visually distinct and drags only its own scroll.

The label now says what it does instead of implying what it doesn't

## [1.17.0] — 2026-08-19

### Added

- **A profile that masks the birth date without removing Original Attributes Sequence is now flagged.** The birth date mask rewrites the top-level Patient's Birth Date and nothing else, which is enough for ordinary images — but a study that has already been de-identified once keeps the values that were changed inside Original Attributes Sequence (0400,0561), so a real birth date could leave in the export while the visible field read as masked. Two things now say so: the profile editor and the Modification dialog show a note beside the Birth date mask when the profile does not remove that sequence, naming the tag to add; and the completion summary reports how many exported files actually still carried a birth date inside a sequence, counted from the files themselves rather than guessed from the profile. Neither blocks a run — most studies carry no such sequence — and the shipped profiles already remove it, so nothing changes for them

### Changed

- **Scanning a folder is dramatically faster, in three ways that compound.** Reading a folder into the tree only needs each file's patient, study and series identifiers, which sit at the very start of the file — but the scan read every file from beginning to end to get them, so the time it took followed the size of a study rather than the number of files in it. It now stops reading as soon as it has what it needs: measured over 1,500 files totalling 13 GB, 6.4 MB read instead of all of it, and under a second instead of twelve. Several files are read at once, which matters on a mechanical drive where most of the elapsed time is spent waiting for the disk to find each one (`DICOMQR_SCAN_WORKERS` changes how many, if the default does not suit a particular drive). And the scan now compares each file against the size and modification time already recorded in the index, opening only what is new or has changed — so a folder nothing has been added to needs no file opened at all, and re-scanning becomes a walk of the folder and nothing more. The same faster read is used when indexing files after a retrieve and after an import, so those are quicker too. Files that store their tags in an unusual order — which the DICOM standard does not permit, but which nothing prevents — are still read the old way, so nothing can go missing from the tree
- **Scan reports what it found, and a new Rebuild button re-reads everything.** Progress now reads `Scanning… 1,200 of 35,489 files` rather than an unbounded tally, and a scan finishes by saying what actually changed: `Found 12 studies, 100 series — 43 added, 2 removed`. Because Scan now trusts what the index says about a file, Rebuild sits beside it for the times you suspect the index rather than the folder — it reads every file and replaces the index outright, which is what Scan used to do. A scan that cannot read part of the folder (a permissions problem, a drive that has gone away) leaves the index alone rather than treating the files it could not see as deleted

### Fixed

- **A malformed DICOM file can no longer crash the application.** The DICOM parsing library raises a panic instead of an error on certain corrupt datasets. Two paths already guarded against that; the other eleven did not, and because they run on background worker threads — the modification engine, the mask review scan, the series scanners, the folder scan, the C-GET receive path — a single bad file took the whole application down with it, in the middle of an export or a retrieve, without naming the file responsible. Every parse now runs behind the same guard, and a file that trips it becomes one reported failure while the rest of the run continues: an export lists it in the completed-with-errors dialog, a retrieve fails just that sub-operation, and the Activity Log records which file and why. A modification run also cleans up the half-written file it was producing, so a failure never leaves a truncated study member in the export
- **A large study no longer risks exhausting memory during an export.** Exports that decompress — anything with pixel masking or an output transfer syntax — process several files at once, and a multi-frame acquisition that is modest on disk can need hundreds of megabytes once decoded, with the decoded frames, the re-encoded output and the original all held at the same time. Four of those together could exhaust memory on a smaller machine, and that ends the whole export at once rather than failing a single file. A run now works to a memory budget sized from the machine's installed RAM (a quarter of it, between 512 MB and 4 GB), holding a file back until there is room for it. Small files still process at full speed; a file larger than the entire budget runs on its own rather than being refused. Exports that only change tags are unaffected, and nothing about the exported files changes either way — only the order work is admitted in. `DICOMQR_MODIFY_BUDGET_MB` overrides the figure if it is ever needed for diagnosis
- **A DICOMDIR index that could not be built correctly is now reported instead of written.** The record links inside a DICOMDIR are byte positions, filled in after the file has been laid out once. If that step had ever failed to find the fields it fills — which a change to how the underlying library encodes them could cause — the positions would have stayed zero, and the result is the awkward kind of broken: a file that opens, lists the right patients and studies, and yet leads a viewer to nothing, because a position of zero means "no record". It would have been written and reported as a success. Each of those fills is now checked, and a failure ends the index build with a reason in the completion summary. The exported DICOM files are unaffected either way
- **Files received with an unusual Patient Name can no longer be written outside the download folder.** A Patient Name, Study Description or Series Description consisting only of dots — `..` being the meaningful case — was used as a folder name verbatim, and the operating system reads that as "the folder above", so the file landed one level outside the download folder where nothing else in the application would find it again. This affected C-MOVE, C-GET and Import alike, Import most of all since it reads folders from outside media. Such a name is now defused, and the destination is re-checked before writing, falling back to the flat layout if it would ever fall outside. Folder names for ordinary values are byte-for-byte unchanged, so existing download folders are untouched

## [1.15.0] — 2026-08-10

### Added

- **The mask review window gains the viewer's filmstrip** — a series that contains clips now shows one thumbnail per image between the picture and the slider, decoded in the background with the current image outlined; click a thumbnail to jump straight to it, exactly as in the viewer. ## [1.14.0] — 2026-08-08

### Added

- **Burned-in PHI can be masked out of exported images** — a modification profile gains *mask regions* (new dicomqr-only `maskregions` key), which blank rectangles of the image itself on the way out. Tag rules cannot reach a patient banner an ultrasound machine printed into the pixels; this is what removes it. Geometry is stored as fractions of the image rather than pixel coordinates, so one profile covers a study whose series differ in size, and rectangles round outward — half a row of leftover text is still PHI. A second mode, *outside the ultrasound region*, takes its geometry from the file's own region calibration sequence instead of a hand-drawn rectangle: banner layout varies by vendor and preset, but the calibrated image region is always stated, and a duplex study's two panes mask to their bounding box so the gap between them keeps its content. Regions marked here apply to that run only, like every other control in the dialog. The section is shown even for a profile that masks nothing — a study whose analysis screens carry a banner is exactly when the absence of masking needs to be noticed

- **A profile that masks a few images no longer decompresses the whole study** — masking requires uncompressed pixels, and the engine decompressed every compressed file as soon as a profile carried any mask region, whether or not the region applied to that file. Regions are now resolved against each file's header before any frame is decoded, so files nothing applies to keep their original compression and are copied through as before. On a 177-file echo study, masking one image went from 75 seconds and a 1.4 GB export to 0.1 seconds and 69 MB for the same 25 files; a profile that genuinely masks every image is unchanged, since that work is required

Because the shipped base-deident profile remaps UIDs, this affected every run made with it. ### Removed

- **Tag aliases (`tags.json`)** — the alias map let a profile refer to a tag by phrase (`PatientName=ANON`) and predated the tag picker, which now names every tag from the standard DICOM dictionary. Keeping both meant two naming authorities, and renaming an alias silently orphaned every profile that used it. The whole subsystem is gone: nothing reads `~/.dicomqr/tags.json`, it is no longer seeded, and a tag must be written as `GGGG,EEEE`. The shipped profiles were recoded accordingly. **A profile copied from dicomtool that refers to tags by phrase must be recoded before it will run here** — dicomtool retains aliases, so this is a deliberate divergence. An existing tags.json is left on disk rather than deleted, and is simply ignored
- **Mask top pixel rows** — the burned-in-annotation row masking option is removed entirely (profile field, engine, editor and dialog controls) ahead of a planned replacement. This is a deliberate divergence from dicomtool, which retains `maskrows`: a dicomtool-authored `maskrows` value is now ignored by dicomqr and stripped when the profile is next saved from the editor

### Internal

- `transcode.go` — the conversion itself extracted to `convertDatasetSyntax(ds, sourceTS, targetTS)`, which operates on a parsed dataset so both callers share one implementation: `transcodeDICOMFileToTemp` wraps it in file I/O for the receive path (behaviour unchanged, covered by the existing transcode tests), `processFile` calls it directly on the dataset a modification has already transformed. `datasetTransferSyntaxUID` reads (0002,0010) from a dataset, since the modify path never revisits the file. `canDecompressSyntax` gains `.57`/`.70` gated on `jpegLosslessAvailable`; `decompressPixelData` dispatches to a new `jpegLosslessFrameToNative`, which shares `planarSamplesToNative` with `j2kFrameToNative` (the two decoders return identical planar int32 output). `acceptedSyntaxesFor` is deliberately untouched, and `TestAcceptedSyntaxesFor` now asserts JPEG Lossless stays out of it
- `modifyengine.go` — `modifyParams.targetTS`; conversion applied last in `processFile` (decompression rewrites Photometric Interpretation and Planar Configuration and must have the final say over them); `modifyWriteOpts` adds `SkipVRVerification`+`SkipValueTypeVerification` when a conversion is requested, since emitting Explicit VR for elements parsed under Implicit VR would otherwise fail files that write fine untouched; `zipSink.write` takes `[]sdicom.WriteOption` rather than a fixvr mode string. A target syntax counts as actionable in `hasAction`, so a convert-only profile is legal
- `modifyprofile.go` — `TransferSyntax` field, override-wins merge rule, `modProfileTargetSyntax` (an unrecognised token is an error, never a silent "as stored"), and the `tsExportLabel*` constants plus label⇄token mapping shared by both editors. Also `canonicalTagRef`/`normalizeModProfile` (canonicalisation on load, at every depth, keeping unparsable entries verbatim), `tagMatchKey`/`setMatchKey` (the parsed-tag comparison `mergeModProfiles` now uses in all four places it matched strings), and `validateSetValue` with the VR helpers `isDICOMTime`/`isDICOMDateTime`/`isDICOMUID`
- `setvalues.go` (new) — `setValueList`/`setValueRow`, the rebuilt-VBox row list shared by both profile editors; `attach` supplies the picker's parent window after construction, since both editors build their controls before `openOwnedWindow` exists to give them one, and construction has to stay window-free for `validate()` to remain test-drivable
- `TagConfig`, `loadTagConfig`, `modifyTagsPath`, `defaults/tags.json` and the `aliases` parameter threaded through ~76 call sites are deleted; `tagDisplayName` is a pure dictionary lookup, which also removes the nondeterminism where two aliases pointing at one tag made the displayed name depend on Go's map iteration order. `checkTagLines` lost its spelling-preservation machinery (`origRemoves`/`origKeep`) and `mergeTagSelection` now regenerates canonically
- `modify_j2k_test.go` / `modify_jpeglossless_test.go` (new, tag-gated) — end-to-end conversion of compressed input asserting bit-exact pixels, plus an as-stored run proving compressed pixel data survives a modification untouched. Nothing previously exercised the modification engine on encapsulated pixel data at all
- `modify_test.go` / `transcode_test.go` — folder and zip conversion, source left untouched, an undecodable source reported as a failed file naming the syntax, base-chain inheritance of the new field, and the dataset-level conversion contract

## [1.12.0] — 2026-08-03

### Added

- **Ultrasound studies play as chapters, one per clip** — a series holding multi-frame instances now opens in *chapter mode*: one chapter per instance, the frame slider scoped to the chapter on screen, and a **transport bar** beneath it (play/pause, sweep, playback rate, previous/next chapter) over a **filmstrip** of thumbnails, one per chapter, clicked to switch. Previously such a series was flattened onto a single slider spanning every frame in it — the sample echo study was one 5,256-position scrub with no seam between one loop and the next and no way to play any of them. Each chapter keeps its own frame position, rate, sweep setting and running state, so leaving a loop and coming back resumes it where it was. `Space` plays/pauses; `Ctrl+Left`/`Ctrl+Right` step chapters; the wheel and arrow keys move within the chapter as before. A still is a one-frame chapter with its transport disabled rather than a dead button, and a series with no multi-frame instance (CT, MR) is untouched, keeping its existing one-position-per-image slider
- **Cine plays at the rate the clip states** — read from `RecommendedDisplayFrameRate`, `CineRate`, `FrameTime`, `FrameTimeVector` or `ActualFrameDuration`, in that order of preference, and overridable per chapter from the transport. A clip stating none plays at 15 fps. `PreferredPlaybackSequencing` selects sweep (forward then backward) over looping, and `StartTrim`/`StopTrim` bound the loop without hiding frames from the slider. Every value is treated as untrusted: zero, negative and four-digit rates all appear in real files, and each is rejected or clamped rather than being allowed to stall or spin playback. The three rate attributes stored as integer strings are read as such — a decimal-only reader silently skips them in favour of a lower-priority attribute, which reads as "playback is a bit fast" rather than as a bug
- **Chapters are labelled from what the file actually says** — image comments, protocol name or a stated view code where present; failing those, what kind of ultrasound image it is (`2D`, `Colour flow`, `PW Doppler`, and combinations for duplex), derived from the region calibration sequence. Real echo studies routinely carry none of the naming attributes — the sample study has no `ImageComments`, `ProtocolName` or `ViewCodeSequence` on any of its 88 clips — so this is often the only thing distinguishing one clip from another besides its thumbnail. A candidate with no letter in it is skipped as an identifier rather than shown as a name (the echo study writes `0001` in `ImageType`; the SPECT study writes `15003.0.68612207@` in `ProtocolName`)
- **The active clip is buffered so playback runs at its stated rate** — decoding one 1016×758 echo frame costs ~18 ms, leaving a 30 fps clip under two frames of headroom on one core, so playing from disk judders. The chapter on screen is decoded across every core into memory — ~0.3 s for a 53-frame loop — after which playback is a memory read; frames land in order, so a clip can be scrubbed and played before buffering finishes. One clip is held at a time, capped at 384 MB; a clip too large for that loops over the frames that fit and says so in the counter, with the rest still reachable by scrubbing

- **Multi-phase MR series navigate one phase at a time** — a series that covers the same slice stack several times over (in-phase/out-of-phase pairs, diffusion b-values, dynamic timepoints) previously presented as one flat slider: scrolling walked all of phase 1 and then started over at the top of phase 2, and comparing phases at one anatomical position meant scrubbing a full stack-length away and back. Such a series now opens with the slider spanning one phase and a **Phase dropdown** in the bottom bar; switching phases (or pressing **P** to cycle) keeps the slice, zoom, pan and window, so it is a same-slice toggle — the flicker comparison an in/out-phase pair is read with. Detection is structural rather than tag-driven: the instance-ordered slice locations must partition exactly into K ≥ 2 identical runs (stored blocked or interleaved) under one image orientation — chosen because real series defeat any single tag (the sample study's in/out pair is distinguished by `EchoNumbers`, but its diffusion series carries identical echo attributes on both b-values and an empty `DiffusionBValue`). Tags then *name* the phases: echo number/time ("Echo 1 (TE 2.38 ms)"), the vendor sequence name ("ep_b50t" / "ep_b800t"), temporal position, or acquisition number, falling back to ordinals. Anything irregular — mixed orientations (localizers), uneven phases, repeated positions within a run, a bolus-tracking series of many timepoints at one location — keeps today's flat list. Verified against a real abdominal MR study: the 200-file in/out-phase series presents as 2 × 100 with echo labels, the 100-file diffusion series as 2 × 50 with b-value labels, and the ADC and Care Bolus series correctly stay flat

### Fixed

- **Streak artefacts during cine playback on NVIDIA GPUs** — while a clip played (or after hovering the viewer's controls), white glyph-shaped streaks radiated across the *other* dicomqr window, apparently growing from one corner. The cause is NVIDIA's **Threaded Optimization** driver feature, which corrupts multi-window OpenGL rendering: diagnosed with a minimal two-window Fyne app containing no dicomqr code (Fyne 2.7.3, 2.7.4 and 2.8.0 all reproduce; ~170 widgets of any kind in the animating window trigger it within seconds, fewer widgets just take longer; a close-up shows the victim window's own text drawn with garbage geometry — and since the animating window repaints every 33 ms, its own corruption self-heals invisibly, which is why only the quiet window shows damage). No GL error is ever raised, and every application-side counter-measure — shared GL contexts, `glFinish` between windows, unconditional uniform uploads — fails; switching the driver profile's Threaded Optimization off stops it completely (verified on an RTX A6000). dicomqr now writes that profile setting for its own executable automatically at startup through NVAPI's driver-settings API — the same store the NVIDIA Control Panel writes — so no user has to find the switch; the write is checked-not-rewritten on later launches, takes effect at latest from the following launch, and is a silent no-op on non-NVIDIA systems. If the write fails (locked-down driver store), the Activity Log carries the manual instructions
- **Status text no longer perturbs window geometry at display rate** — the frame counter re-labels ~10×/s during playback, and with a proportional font nearly every new number changes the label's width — which changes the window's minimum size, which makes Fyne re-apply the window's size limits, which GLFW implements on Windows as `MoveWindow(..., repaint=TRUE)`: a full repaint of the window frame ten times a second. The counter, the W/L info label and the chapter label are now wrapped in a layout that reports a high-water-mark minimum size, so re-labelling never touches window geometry (the same path fires in earlier releases during window/level drags). Distinct from the NVIDIA artefact above — this one wastes work and can flicker the frame, but was not the source of the streaks

- **Multi-frame files preview every frame, not just the first** — previewing a SPECT reconstruction, projection set or any other multi-frame object showed a single image with the counter reading `1 / 1`: the viewer navigated *files*, and rendered only frame 0 of each. Most modalities store one image per file, so this was invisible on CT and MR, but nuclear medicine stores a whole acquisition in one file — everything after the first frame was unreachable. The viewer now navigates *frames*: each file's frame count is read during the header pass that already orders the series, and every frame becomes a navigable slice, so the counter, slider, wheel and arrow keys span the whole acquisition. The study overview thumbnail for such a series is likewise the middle frame of the acquisition rather than its first. Files are parsed once and cached, so stepping through a multi-frame acquisition decodes one frame per step instead of re-reading the file — a 240-frame projection set scrolls without re-parsing. Verified against a real SPECT/CT study: the 240-frame projection set, the 128- and 87-frame reconstructions, and both 42-frame recons now expose every frame, each decoding to distinct pixel data (the only repeated frames are the genuinely blank slices at the ends of a reconstruction volume)

### Changed

- **Activity Log opens at Errors only and renders instantly at any level** — the dialog now always opens at the Errors only view (problems first, verbosity on demand; the short-lived `logViewLevel` setting is retired — an unknown key in settings.json is ignored, so existing files need no migration). The log body moved from a monolithic text widget — which laid out every line at once, making a switch to Everything noticeably sluggish with a full 5000-line ring — to a virtualized list that renders only the visible rows, so any level switch or filter keystroke appears instantly regardless of ring size. CT and MR store one frame per file and never hit this; NM/SPECT stores the entire acquisition as a single file of 40–240 frames (verified against a real SPECT/CT study: the 240-frame projection set and every reconstruction froze; all now load in milliseconds). ### Fixed

- **Closing the application can no longer leave a phantom dicomqr.exe in Task Manager** — closing the window sometimes left the process alive (windowless, still holding the SCP port) after the UI disappeared. An audit ruled out the suspected causes: every termination path (window close, File > Quit, the app-stopped lifecycle hook, the panic safety net) already stops the C-STORE SCP and releases its port via a non-blocking, idempotent `Stop()`, and every file handle in the receive/transcode/export/settings/log paths is closed on all branches (and could not keep a process alive regardless). The actual cause is a race in Fyne 2.7's quit path: the run loop drains its function queue and only afterwards marks it drained, so work posted in that gap — which includes Fyne's own delivery of the OnStopped hook — is stranded with its poster blocked forever; `ShowAndRun` then never returns. Since the app cannot close that window, every termination path now arms a 3-second exit watchdog *after* settings, catalog, and SCP cleanup have finished: a normal shutdown exits before the timer fires, and a wedged one is force-terminated with a log line (`exit watchdog: shutdown wedged`) in dicom.log
- **Collapsing a branch no longer leaves the top of a tree blank** — closing an expanded node low in a scrolled-down tree could leave the rows above it unrendered (sometimes the entire tree area blank) until an unrelated scroll or refresh happened to repair it. Root cause is a virtualization bug in Fyne's tree widget (v2.7.3): it culls rows against its own copy of the scroll offset, synced only by the scroller's scroll callback — but when a collapse shrinks the content, the scroller clamps or resets its offset through paths that never fire that callback, so the tree keeps culling rows that are actually inside the viewport. Every tree in the application (query results, Local Browse, Import, tag viewer) now queues a refresh after each branch close, which re-syncs the offset and redraws the visible rows; the Collapse All buttons, which bypass the per-branch close callback entirely, scroll to the top first (the tag viewer already did this — now shared by all four trees) — the v1.9.0 exe imported `libwinpthread-1.dll` (GCC's threading runtime, dynamically linked by default), so it failed to start on any machine without MSYS2 with "System error: libwinpthread-1.dll not found". Both build scripts now pass `-extldflags=-static`, linking the GCC runtime statically; the exe's only remaining imports are standard Windows system DLLs
- **Preferences Apply can no longer silently zero settings it has no control for** — the Apply handler rebuilt the whole `Settings` value as an explicit field list, so any field missing from that list (as `retrieveStallTimeoutSec` was, resetting hand-tuned values back to the 120 s default on every visit) was silently erased. ## [1.8.0] — 2026-07-23

### Changed

- **The transfer syntax requirement is now enforced in the receive path, per file, before it reaches disk** — requiring 'Explicit VR LE' or 'Implicit VR LE' in a server profile guarantees every retrieved file is stored in exactly that syntax. Negotiation (the C-GET proposal list and the C-MOVE storage SCP's accepted presentation-context set) offers the required syntax first — a transcoding-capable server sends it and nothing needs converting — followed by the syntaxes the application can convert locally (the other uncompressed VR, JPEG Baseline/Extended, and JPEG 2000 in openjpeg builds). A file arriving in any non-required accepted syntax is transcoded **while still a temp file**, so the download folder only ever holds conforming files — there is no post-retrieve batch pass, no fire-and-forget goroutine, and no window where a wrong-syntax file exists on disk. A failed conversion fails that C-STORE sub-operation, and any failed sub-operation or target error aborts the whole retrieve with a dialog reporting the required syntax, the failure details, and how many (all-conforming) files arrived before the abort. The completion status reports how many files needed local conversion, making a non-transcoding server visible at a glance. This replaces v1.7.0's 'preferred' negotiation and its post-retrieve 'Guarantee uncompressed on disk' pass, which could silently leave a study as a mix of syntaxes (observed 2026-07-23: ~half a study left as JPEG 2000 despite the guarantee, and study- vs series-level retrieves gave differing results)
- **'Guarantee uncompressed on disk' checkbox removed** — conversion is now intrinsic to requiring a syntax. The `ensureUncompressed` settings field is ignored on load; the pre-v1.7 `transferUncompressed` flag now migrates to `transferSyntax: "explicit-le"` alone
- **Re-retrieves replace syntax-mismatched copies** — with a required syntax set, an existing on-disk file whose transfer syntax differs from the requirement is replaced by the incoming (converted-if-needed) copy; matching or unrestricted files are skipped silently as before

### Fixed

- **`dicom.log` and the Activity Log were always empty in release builds** — the log output went through `io.MultiWriter(os.Stderr, file, ring)`, and in a `-H windowsgui` build launched from Explorer, `os.Stderr` is an invalid handle whose writes fail; `io.MultiWriter` stops at the first failing writer, so nothing ever reached the log file or the Activity Log dialog. Every sink is now wrapped in a failsafe writer (file first), verified end-to-end against a detached GUI launch. Each session starts with a version/build header line, and two previous sessions are kept (`dicom.log.1`, `dicom.log.2`) so evidence of a hang survives restarts
- **`dicom.log` no longer goes silent after the session-start line** — even with the failsafe writers, real sessions were observed (2026-07-23) whose log files contained only the header: every later write to the session's long-lived file handle vanished without an error surfacing, which destroyed the evidence needed to diagnose that day's transfer-syntax incident. The file sink no longer holds a handle at all — it reopens the log in append mode for every write, so nothing that invalidates a previous handle (a second instance's log rotation, antivirus interference, a recreated directory) can kill file logging for the rest of a session; write failures are counted and the first is reported to the Activity Log ring. The ring and stderr sinks are also now wired even when the home directory is unavailable (previously the whole redirect was skipped and windowsgui builds lost all logging). Sessions additionally log their starting configuration (profile count, download folder, AE title, SCP port), each retrieve's method and required transfer syntax, and every settings save — so a log file alone can reconstruct what the app was configured to do
- **Settings saves no longer fail silently** — `saveSettings` returned on any error without a trace, so a failed write left `settings.json` stale while the app behaved as configured (observed 2026-07-23: mid-session preference changes that never persisted). The atomic-rename step is now retried (3 × 150 ms) to ride out antivirus/indexer holds on the destination, every save logs its outcome, and a save failure from the Preferences dialog shows an error dialog stating that the settings apply to this session only
- **Negotiation visibility** — the log now records, for every association in both directions, each presentation context's offered transfer syntaxes and the chosen one, rejections with the local accepted set (always logged), and the storage SCP's active transfer policy per incoming association — enough to diagnose transfer-syntax negotiation problems from the log alone

- **C-GET retrieves of whole studies (≥124 instances) no longer wedge partway through** — the DIMSE dispatcher kept locally-initiated commands and peer-initiated commands in one map keyed by message ID alone. Our C-GET command takes message ID 124, and the PACS numbers its C-STORE sub-operations from 1 upward — so the 124th instance of a retrieve collided with the C-GET command itself and was mis-routed to the C-GET response loop instead of the C-STORE handler, stalling the transfer. Series-level retrieves stayed under the threshold, which is why only study/patient selections failed. Message IDs are scoped to the initiating AE (PS3.7), so the dispatcher now keeps peer-initiated commands in their own keyspace; responses route only to local commands, requests only to peer commands
- **C-GET received files were stamped with the wrong transfer syntax** — every file received over C-GET was labelled with the *query context's* negotiated transfer syntax instead of the storage context the instance actually arrived on. Harmless while both were uncompressed variants, but corrupting once storage contexts can negotiate JPEG 2000 (v1.7.0 preference fallback): a JPEG 2000 payload would be saved with meta claiming Explicit VR LE. The C-STORE handler now takes the transfer syntax from its own sub-operation's presentation context
- **C-GET parity fixes** — final status 0xBxxx (sub-operations complete with failures) is now treated as a completed transfer with a logged warning, matching the C-MOVE behaviour, instead of failing the whole retrieve; a peer request with no registered handler is logged and dropped instead of crashing the process by invoking a nil callback
- **Retrieves no longer hang forever on non-image series (SR, Presentation State, encapsulated PDF)** — some PACS C-MOVE agents stall while sending objects that carry no pixel data: the association stays open but no further data or progress response ever arrives, and the retrieve previously hung until the application was killed. A stall watchdog now aborts the retrieve after 120 seconds of total silence (no C-MOVE-RSP, no received file) with a status message and a dialog explaining the likely cause and recommending Retrieve method C-GET or Auto for the affected server. The timeout is configurable via `retrieveStallTimeoutSec` in settings.json (-1 disables it, for slow tape archives)
- **Cancelled and stalled retrieves now tear the association down** — cancelling a retrieve (or a watchdog abort) previously left the DIMSE goroutine blocked forever and the TCP association open; it now sends A-ABORT, unblocks the pending operation, and reaps the goroutine. Applies to C-MOVE, C-GET, and Push to PACS

## [1.2.0] — 2026-06-17

### Added

- **Request uncompressed transfer syntax** — each server profile now has a "Request uncompressed transfer syntax only" checkbox in the profile editor. When enabled, dicomqr restricts the A-ASSOCIATE-RQ presentation contexts to Explicit VR Little Endian and Implicit VR Little Endian only, causing a conformant PACS to transcode compressed pixel data before delivery. Applies to both C-GET (SCU transfer syntax list) and C-MOVE (embedded C-STORE SCP rejects compressed syntaxes at association time with `PresentationContextProviderRejectionTransferSyntaxNotSupported`).

### Fixed

- **Image viewer: compressed pixel data error** — files using JPEG 2000 (Lossless/Lossy), JPEG-LS (Lossless/Near-Lossless), JPEG Lossless Non-Hierarchical, or RLE Lossless transfer syntaxes now display a clear, actionable message ("use Open in Viewer") instead of the cryptic "Invalid JPEG Format: missing SOI marker" error that appeared because the suyashkumar/dicom library unconditionally passes all encapsulated frames to `jpeg.Decode`
- **Image viewer: undefined-length uncompressed pixel data** — DICOM files from certain vendors that store uncompressed pixel data with an undefined-length VL are now decoded correctly. The suyashkumar/dicom library previously treated undefined-length pixel data as encapsulated (JPEG), causing the same JPEG decode failure on some systems. A raw-pixel fallback path now reinterprets the bytes natively using the image dimensions, bit depth, rescale parameters, and photometric interpretation from the dataset; this was the root cause of the "same data works on one system but not another" behaviour

### Internal

- Vendored `thirdparty/go-netdicom` extended: `ServiceProviderParams.AcceptedTransferSyntaxes []string` — when non-empty, the service provider selects only offered transfer syntaxes that appear in the list during A-ASSOCIATE-RQ negotiation, rejecting contexts where none match; `contextmanager.go` patched to iterate all offered syntaxes rather than blindly picking the first
- `viewer.go` — `unsupportedTransferSyntaxNames` map for proactive transfer syntax detection; `renderRawPixelFallback` for native pixel decode of misidentified encapsulated frames; `dicomIntParam` helper for integer dataset lookup

- **Results tree sorting** — patients alphabetical by name; studies chronological by date; series numeric by series number
- **Select All / Clear Selection** — buttons in the retrieve panel; **Esc** also clears the current selection
- **Expand All / Collapse All** — buttons above the results tree

- **Connect timeout** — per-profile **Connect timeout (s)** field (default 10 s) prevents indefinite hangs on unreachable servers
- **Cancel connect** — the **Disconnect** button becomes **Cancel** while connecting and aborts the in-flight C-ECHO

- **Inline server profile validation** — AE Title (required, ≤ 16 chars) and Port (1–65535) are validated in the server editor

### Changed
- **Results tree selection behaviour** — parent/child-aware: selecting a node selects all its loaded descendants; narrowing and per-child deselection behave intuitively; expanding a selected node auto-selects newly loaded children
- **Filter popup** — the Filters dropdown is a modal popup that auto-dismisses on outside click
- Results tree starts fully collapsed after each search; expanding a study triggers the series C-FIND

### Fixed
- **SCP port left locked on exit** — closing the window (X), File → Quit, and any other termination route now stop the embedded C-STORE listener and release its port; previously only the Disconnect button did, so the port could stay bound after the app closed and block a restart. `StorageSCP.Stop()` now closes the listener synchronously, and an app-stopped lifecycle hook acts as a final safety net. If the port is still in use when connecting (e.g. after an unclean kill that bypasses shutdown), the SCP retries the bind briefly and then reports a clear, actionable message ("port N is already in use — another copy of dicomqr may still be running…") in a dialog rather than a raw socket error
- **Connection-state data races** — the active client, C-STORE SCP, query context, and active profile are now guarded by a mutex, removing the race (and possible nil-deref) between disconnect on the UI goroutine and an in-flight retrieve
- **Download directory validated up front** — a retrieve now fails fast with a clear message if the download folder cannot be written, rather than erroring per received file
- **Filters popup validation error** — re-opening the Filters panel after a search no longer shows a spurious date-parse error on empty date fields
- **Cancel retrieve** — pressing Cancel reliably shows "Retrieve cancelled"; the C-STORE and C-GET callbacks check `ctx.Err()` before posting UI updates
- **Error 45056 (C-MOVE warning) recovery** — DICOM warning status 0xB000 is no longer treated as fatal; multi-series retrieves continue and the final status reports warning counts
- **Path-length guard** — each folder component is truncated to 64 characters; the path falls back to a flat `<downloadDir>/<sopInstanceUID>.dcm` layout when it would exceed 255 characters
- **Windows reserved device names** — path components matching `CON`, `NUL`, `PRN`, `AUX`, `COM1`–`COM9`, `LPT1`–`LPT9` are prefixed with `_`

### Internal
- Data-race fixes for `state`, `StorageSCP.downloadDir`, and `scp.OnFileReceived` (mutex-guarded)
- Atomic settings write (temp-file + `os.Rename`) to prevent settings corruption on crash
- `sort.Search`-based sorted insert replaces `sort.Slice`-on-every-insert (O(N log N) vs O(N² log N))
- `applyFilter` deferred out of the per-insert path — called once per batch
- `tree.RefreshItem(id)` replaces full `tree.Refresh()` after series lazy-load
