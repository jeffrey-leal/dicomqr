# dicomqr

A Fyne-based Windows GUI application for querying and retrieving DICOM files from a PACS server.

## Build

Requires CGO and the mingw64 GCC toolchain. **Must be built from an MSYS2 MinGW64 terminal.**

JPEG 2000 decoding (`-tags openjpeg`) requires the OpenJPEG library, and JPEG Lossless decoding (`-tags jpeglossless`) requires libjpeg-turbo 3.x, each installed once with:
```bash
pacman -S --needed mingw-w64-x86_64-openjpeg2
pacman -S --needed mingw-w64-x86_64-libjpeg-turbo
```
Release builds enable both tags (`-tags "openjpeg jpeglossless"`; libopenjp2 and libjpeg are statically linked — single self-contained exe). Omitting a tag still builds; the corresponding files then report "support not built in" and suggest the external viewer.

All builds must pass `-extldflags=-static` so GCC links its own runtime (libwinpthread, libgcc) statically; without it the exe imports `libwinpthread-1.dll` and fails to start on machines without MSYS2.

Open MSYS2 MinGW64, then:

```bash
export PATH="/c/Program Files/Go/bin:$PATH"
cd /c/Users/jeffr/source/repos/dicomqr
```

Release build:
```bash
CGO_ENABLED=1 CC=/c/msys64/mingw64/bin/gcc.exe GOAMD64=v3 \
  go build -tags "openjpeg jpeglossless" -ldflags="-s -w -H windowsgui -extldflags=-static -X main.buildDate=$(date +%Y-%m-%d)" -o dicomqr.exe .
```

Development build (with debug info):
```bash
CGO_ENABLED=1 CC=/c/msys64/mingw64/bin/gcc.exe \
  go build -tags "openjpeg jpeglossless" -ldflags="-extldflags=-static -X main.buildDate=$(date +%Y-%m-%d)" -o dicomqr.exe .
```

## Project structure

| File | Purpose |
|---|---|
| `main.go` | App entry point, window layout, tab container, menu bar, connection panel, query panel, retrieve panel, status bar, connection/SCP LEDs |
| `resultsmodel.go` | `resultsModel` — tree data structure for C-FIND query results |
| `queryrow.go` | `queryRow` — Fyne widget for results tree rows (hover tooltip, right-click menu). Implements `desktop.Mouseable` only to capture the click's modifiers in `MouseUp`, which Fyne calls immediately before `Tapped` — `fyne.PointEvent` carries none |
| `nodeselection.go` | `nodeSelection` — the one selection model behind all three `queryRow` trees (Query Results, Local Browse, Import). `Click` applies the **Windows convention**: plain click = `Select` (replaces the selection; re-clicking a row selected among others narrows to it), **except that a plain click on the row that is the whole selection deselects it** (`soleSelection` — the row plus only the descendants its selection fanned out to). That one is an addition to the convention: Explorer has empty space to click, these trees usually have none, and a lone selected row could otherwise only be dropped with Ctrl+click or Clear Selection, which was field-reported as broken. The branch arrow is Fyne's own control and never reaches `Click`, Ctrl = `Toggle`, Shift = range replacing the selection, Ctrl+Shift = range added to it. Multiple selection always takes a modifier — a plain click that accumulated was how a forgotten row got swept into a Retrieve/Push/Delete. Branch selection fans out to loaded children, and `Toggle` repairs ancestor flags so a branch is flagged only while every child is. **Ranges run between siblings only** — a deliberate departure from the convention (which spans every visible row), since a range across independently collapsed/filtered branches has no unambiguous meaning; a non-sibling Shift+click falls back to a single-row click. Right-click menus act on the clicked row only and never change the selection — also a departure, left in place deliberately. The tag viewer (Fyne's native single selection) and tag picker (per-row checkboxes) do not use this and should not. **Every operation repaints once** (`flush`): the subtree helpers only change the map and record what changed, then one `RefreshItem` if a single row changed, otherwise one full `Refresh`. Fyne 2.7.3's `RefreshItem` runs the tree's whole `Layout`, so the old per-row repaint made Select All over a large expanded or filtered tree quadratic — a multi-second freeze (`TestNodeSelection_OneRefreshPerOperation`) |
| `dicomnet.go` | `DicomClient` — SCU wrapper for C-ECHO, C-FIND, C-MOVE, C-GET, C-STORE, Modality Worklist |
| `storagescp.go` | `StorageSCP` — embedded C-STORE SCP listener that receives C-MOVE deliveries. `patientFolderName`/`studyFolderName`/`seriesFolderName` are the one authority for the organized hierarchy's names (called by `organizeFilePath`, `resultsModel.localFolderFor` and `exportLayout.relFor`), and each ends in **`safePathComponent`**: a component that is nothing but dots is prefixed `_`, because `sanitize` strips none of the characters in `..` and `filepath.Join` then Cleans it — a `PatientName` of `..` used to write the received file one level *above* the download folder, through C-STORE, C-GET and Import alike. The whole-string dot test (not an exact `.`/`..` match) also covers `...`, which Windows cannot create at all, and can never rename a legitimate folder — which matters, since renaming one orphans everything already downloaded under it. `sanitize` itself is deliberately unchanged: it also builds file names, where a suffix makes traversal impossible, and any change to it would rewrite existing folder names. `organizeFilePath` then re-checks containment with `pathWithinDir` and falls back to the flat layout, so staying inside the download folder is a property of the function rather than of having got the character rules exactly right |
| `localbrowse.go` | Local Browse tab — scan download folder, push to PACS, delete local files, preview routing, Modification submenu (right-click, whole patient/study) and **Modify Selected…** (the selection — how a subset of a study's series is de-identified). `modificationScope` maps a selection onto the only two run shapes the export layout has — one study → study-level, several studies of one patient → patient-level — and **refuses a selection spanning patients**: the export root stands in for one patient, and a profile's Set values would give them all the same identity. There is still no series-level run; a series subset is a study-level run over fewer files. `modificationProfileItems` is the one profile menu both entry points list. `parseLocalFileMeta` is the indexing read behind four call paths (this scan, the Import tab's source scan, and `catalog.ingestPaths` after every retrieve and every import), and it **stops reading once past `localMetaMaxGroup`** — `scanLocalFileMeta`, the technique `scpParseMetadata` uses. That matters because `SkipPixelData` does **not** avoid reading the pixels: the library's `Reader.Skip` is `io.CopyN(io.Discard, …)`, not a seek, so a full parse still pulls every pixel byte off the disk to discard it, making the old scan scale with study size rather than file count. Measured over 1,500 files totalling 13 GB: 6.4 MB read instead of all of it, 649 ms instead of 12.4 s (≈19×, and more than 8-way threading of the old path would have given — threading composes on top but is the smaller half). `localMetaMaxGroup` is **derived** from `localMetaTags` rather than written as `0x0020`: a tag later added in a higher group would otherwise sit past where the scan stops and read as absent from every file, silently. `fullLocalFileMeta` remains as the fallback for a file whose tags are not in ascending order — the standard requires that order and no measured file breaks it, but a missed identifier drops the file from the tree entirely, and the fallback never runs on a conformant file. Values are read with a checked assertion, not `sdicom.MustGetStrings`, which panicked outside the parse boundary's recover on a tag stored under an unexpected VR. `TestScanBench` (opt-in, `DICOMQR_SCAN_BENCH`) asserts the two paths agree file-for-file over a real study. **Progress is paced by `scanProgressInterval` (time), never by a file count**: both callers hand each report to `fyne.Do`, whose queue is unbounded and never blocks, so a per-N-files trigger emits at whatever rate the disk runs at and the UI goroutine must drain every one — each re-texting a width-changing label, which on Windows repaints the whole frame (see `stableMin`). Once the scan itself got ~20× faster the same ~500 updates arrived as a burst and the callback that populates the tree queued behind them, so the tree looked seconds slow when it was instant. **The scan reads files in parallel** (`scanWorkers`, default 8, `DICOMQR_SCAN_WORKERS`) in three phases — walk to collect paths, parse on a worker pool, merge in walk order. A cold scan is bound by *seek latency*: measured on a RAID-0 array of spinning disks, 35,489 files took 5½ minutes (9.3 ms each, one head movement) against 10 s warm, and after early exit the scan reads only a few KB per file, so those minutes are almost all waiting. Eight rather than the CPU count because these workers sleep on the disk where the modification and mask pools compute — and **provisional**, since cold conditions cannot be reproduced on a machine with enough RAM to cache the corpus; the override is how it gets settled. Each worker writes its own index in a `[]scanResult`, so **the merge runs in walk order**: first-write-wins study metadata and the file order inside a series are what the tree shows, and neither may depend on which worker finished first (`TestScanLocalFolderIsDeterministic`). The returned `studies`/`series` slices are sorted by UID — they come out of maps, so their order was randomised run to run even before any of this was parallel; harmless where they go, but not something to leave for the next caller. Progress reporting follows clipBuffer's split (workers only `atomic.Add`, one ticker goroutine publishes), and the phases make the total known up front, so the message is a bounded `N of M files`. **Local Browse's Scan runs `syncLocalFolder`, not `scanLocalFolder`**: it walks, compares each file against the catalog's stamps, and reads only what is new or changed, so an untouched folder opens no files at all and the walk is the whole cost — the difference between minutes and seconds on a cold disk. `walkDicomFiles` uses **`WalkDir`, not `Walk`**, because `Walk` `Lstat`s every entry while `WalkDir`'s `DirEntry.Info()` on Windows returns the data the directory enumeration already produced (verified in Go's source — a cached `*fileStat`, no syscall), so the size and mtime the comparison needs arrive free. It also **counts entries it could not read**, and `filesToRemove` prunes **nothing** when that count is non-zero: files under an unreadable subtree are indistinguishable from deleted ones, and an index briefly stale is recoverable where one that has silently dropped a study is not. `scanLocalFolder` remains the full read, used by the Import tab (an arbitrary source folder has no index to compare against) and by the **Rebuild** button, which keeps `replaceAll` — Scan now trusts the index, and suspecting the index is exactly why someone presses Scan |
| `catalog.go` | `catalog` — persistent SQLite index (`.dicomqr-index.db` in the download folder) backing the Local Browse tree; nil-safe, WAL, single connection. `fileStamps` reads back the per-instance `size`/`mtime` — written since the index was added and, until the incremental scan, never queried — which is what lets a re-scan skip a file: matching stamps mean the copy on disk is the one that was parsed. Resolution is one second (what the schema stores), so a file rewritten within the same second to exactly the same length would read as unchanged; dicomqr never edits its own downloads, and Rebuild is the recovery. `upsertMetas` is `ingestPaths`' counterpart for callers that already hold parsed results — a scan parses its changed files on a worker pool, and handing `ingestPaths` the paths instead would re-parse them. Both write through **`metaUpserter`**, which prepares its four statements once per transaction (modernc's `tx.Exec(sql, …)` prepares and finalizes per call) and skips a patient/study/series row already inserted earlier in the batch — a no-op under INSERT OR IGNORE anyway, recorded only after the insert succeeded, so first-write-wins is unchanged (`TestCatalogUpsertMetasFirstWriteWins`; measured 10,000 files 355 → 94 ms). `replaceAll` and `removePaths` prepare their statements the same way. `ingestPaths` (after every retrieve and import) parses through `parseFilesParallel`, so its results keep the order given |
| `modifyprofile.go` | Modification (de-identification) profiles — `ModProfile`, load/first-run seeding of `~/.dicomqr/profiles.json`, base-chain resolution, tag parsing/display names. **Every tag reference is canonical `GGGG,EEEE`**: `normalizeModProfile` canonicalises on load, and `mergeModProfiles` compares **parsed tags** (`tagMatchKey`/`setMatchKey`) rather than literal strings — a Keep list cancels its base's Removes by tag identity, so two files spelling one tag differently can no longer silently un-cancel a removal and delete a tag the user asked to preserve. An unparsable reference is kept verbatim for validation to report, never dropped. `validateSetValue` checks a Set value against the tag's VR (dates, times, UIDs, numerics, length limits; empty always allowed) — the engine's `buildElement` only ever coerced the numeric VRs, so a `DA` set to `ANON` used to reach the exported files. A Set value of exactly `[GGGG,EEEE]` is a **reference** to another of the same profile's Set values (`setValueReference`, `resolveSetReferences`, `setValueFollowers`): the shipped profile writes `0010,0020=[0010,0010]` so Patient ID follows the new Patient Name, a relationship the Modification dialog used to hold as hardcoded tag numbers. **A reference can never reach the value in the file being modified** — that would copy the real patient name forward into whatever field named it, per file, with nothing on screen to show it. One level only: a reference to a reference is an error, which rules out cycles by construction. `compileModifyParams` resolves before parsing, so the engine only ever sees literals. `modProfileTargetSyntax` maps the dicomqr-only `transfersyntax` field (same `explicit-le`/`implicit-le` tokens as the server profile) to the UID exports are written in, and the `tsExportLabel*` constants keep the profile editor and the Modification dialog naming it identically. **`modProfileDOBAdvisory` is the safeguard for the one thing the birth-date mask cannot reach**: `applyDOBMask` rewrites the top-level `0010,0030` only, where removals, date shift, UID remap and Set values all recurse. In ordinary image objects that suffices — demographics live in the top-level Patient Module, and the sequences referencing a patient (`0008,1120`, `0010,1002`) carry identifiers, not birth dates — but **Original Attributes Sequence (`0400,0561`)** nests the pre-modification values an earlier de-identification changed, so a study processed once before can ship the real birth date while the top-level field reads masked. Removing `0400,0561` takes its nested contents with it, which is why the shipped profiles are not exposed (`TestEmbeddedDefaultsRaiseNoDOBAdvisory` fails if that removal is ever dropped). The advisory must be given a **resolved** profile — a base supplies the removal for most real profiles and a Keep list can cancel it again — and reads only the profile-level Removes, since an override's removals cover its own modality alone. Making the mask recurse was rejected: `replaceInElements` writes one value at every depth, right for a Set rule but wrong for a mask, which has to be applied to each occurrence's own value. `Dicomdir` — a field dicomtool already defines, kept for JSON interop — requests a DICOMDIR (PS3.10 File-set) index alongside the export (dicomdir.go); profile-wide only, like `Zip`, and unlike dicomtool's own `dicomdir:true` it composes freely with `Zip` rather than refusing the combination. `Flat` writes every exported file directly into the export root instead of the patient/study/series hierarchy `exportLayout` otherwise builds, named after its SOP Instance UID rather than kept under its source name — dropping the folders drops the context a source name relied on for uniqueness, so flat mode cannot reuse it. Profile-wide only, like `Zip` and `Dicomdir`, and composes with both |
| `sopclass.go` | The `ignoresopclass` profile filter's vocabulary — `sopClassNames` (well-known storage classes, display only), `secondaryCaptureSOPClasses` (the family the manual recommends listing), UID syntax validation (`validateSOPClassUIDs`, lenient about leading zeros because vendors emit them and a filter that refused the UID a file actually carries could never match it) and `matchesSOPClass`. **Why a SOP-class filter and not `ignoretype SECONDARY`**: surveyed over 55,920 downloaded files (2026-09-03), every document-like series — scanned forms, dose and protocol pages, saved screens — was a Secondary Capture object labelled with the study's imaging modality, no natively classed image series looked like a document, and one kiosk scan carried no ImageType at all, while `SECONDARY` also matches MPR reformats. The engine's `skipsSOPClass` (modifyengine.go) checks the profile's list **and** the matching per-modality override's, unioned — the only file filter honoured inside an override, so a base can skip Secondary Capture for CT/MR/NM/PT while leaving an echo study's measurement screens (Secondary Capture too) to the mask review. Collateral the rule also drops, by design: fused PET/CT renders, MIP cines, Siemens Care Bolus monitoring frames — derived or reproducible, and nothing in the header tells them from a document. Field hook: `DICOMQR_SOPCLASS_SAMPLE=<study folder> go test -run TestSampleIgnoreSOPClassStudy -v .` runs the filter through the real engine and asserts exactly the Secondary Capture and ignored-modality files skip and no Secondary Capture object reaches the export (GHAFOURI CT study: 2,395 files, 29 skipped, 2,366 exported, 0 failed) |
| `setvalues.go` | `setValueList` — the Set values row list (tag chosen from the picker + value entry + delete), replacing a free-text `TAG=VALUE` box in both profile editors. The owning window is `attach`ed after construction rather than passed in, because both editors build their controls before `openOwnedWindow` creates the window the picker parents to — and keeping construction window-free is what lets `validate()` be driven by tests with no canvas. Choose tags… opens the picker with the current tags checked, so it adds and (by unchecking) removes rows; a tag that stays keeps the value already typed. Rows keep the profile's stored order (a group-then-element sort was tried and reverted: the stored order is the author's presentation choice — shipped base-deident leads with Patient Name, not a blank Accession Number — and sorting made Apply rewrite an unedited profile reordered); picker additions append in dictionary order via `mergeTagSelection`, which keeps surviving rows in place, and a row whose reference does not parse stays where the profile put it, visible to be fixed. A value bracketed like a reference but naming no tag (`[patient name]`) is rejected rather than stored as a literal |
| `modifyengine.go` | De-identification engine ported from dicomtool `modify` (identical semantics): set/remove/keep, DOB mask, UID remap (the `uid` suffix option is removed — a profile still carrying it is refused at compile with a message naming Remap UIDs, never silently ignored, and the stored value round-trips untouched), overlay-plane removal (`nooverlays` drops groups 6000–60FE even — the bitmap channel no per-tag rule reaches and pixel masking cannot touch), date shifting (`shiftdays` — DA/DT at any depth, PatientBirthDate excluded), private-tag removal, fixvr, per-modality overrides; `runModification` worker pool writes to an export folder using the PHI-safe layout from `exportLayout` (the export root the user types in the Modification dialog stands in for the patient folder, or patient+study for a study-level run — the only names guaranteed to need typing, since a patient folder is always PHI; everything below keeps its source folder/file name **unless** the tag(s) that name is built from actually changed, in which case that one component is rebuilt with the same rules `organizeFilePath` uses, from `exportNames` read before and after the file's attribute steps — `processFile` captures both into `fileNotes`, so a shifted `StudyDate` or a replaced `SeriesDescription` moves the file into a correctly-renamed folder while an untouched study or series keeps its original name instead of a generic `study-NN`; a remapped SOP Instance UID likewise renames the file itself). `patientFolderName`/`studyFolderName`/`seriesFolderName` (storagescp.go) are the one place that naming scheme is defined — `organizeFilePath`, `resultsModel.localFolderFor` and `exportLayout.relFor` all call them rather than keeping their own copies. `exportLayout.flat` is the alternative to all of that: every file lands directly at the export root, named after its SOP Instance UID (`flatFileName`) rather than kept under its source name — the folder hierarchy a kept source name relied on for uniqueness is exactly what flat mode removes, so reusing the source name would reintroduce the collisions the hierarchy prevented. `flatNames` (a mutex-guarded set of names already handed out) exists only for what a unique-by-construction SOP Instance UID cannot rule out — a genuinely duplicated instance, or a file with none at all — appending a numbered suffix rather than silently overwriting the first claimant or, in a zip, producing two entries with the same name; a nil `*flatNames` (every non-flat `exportLayout`, and the engine's own `relFor` tests) reserves nothing. `runModificationToZip` runs the same pipeline into a single zip archive (temp-file + rename so a failed/empty run leaves no archive). **`zipSink` serializes only the append**: each worker encodes its file into memory, CRCs it and deflates it itself (level 5, archive/zip's own, so the bytes match `zw.Create`'s — `TestZipSinkEntriesMatchCreate`), then takes the lock just for `zw.CreateRaw` + copy; it used to encode and deflate under the lock, one core for the whole archive (measured 120 raw-passthrough 512² slices on 4 workers: 1.79 → 0.67 s). `zipRawHeader` supplies what CreateRaw does not set — the UTF-8 name flag by archive/zip's `detectUTF8` rule, version-needed 2.0/4.5, the data-descriptor flag for a Zip64-sized entry. Already-compressed pixel data (`encapsulatedPixelData`) is **stored**, not deflated; an entry over `zipParallelMaxBytes` (64 MB) is deflated under the lock from its encoded bytes so a worker never holds a second full-size copy. Zip output must stay identical to the folder export file for file (`TestZipExportMatchesFolderExport`). **A run that cannot mask (`rawPixelPassthrough` = `!mayMask`) parses with `SkipProcessingPixelDataValue`**, so native pixel data stays the stored bytes and the writer copies them out byte-identical: the library otherwise reads native data one `io.ReadFull` per sample and writes it one heap-allocating `binary.Write` per sample — measured 25 ms → 0.46 ms per 512×512 16-bit slice, 524,585 → 262 allocations — which made pixel data, not tag rules, most of a tag-only run. Encapsulated data is unaffected (its fragments are raw already), and a conversion between the two LE syntaxes leaves sample bytes as they are. It relies on `convertDatasetSyntax` refusing an Explicit VR Big Endian source (raw BE bytes written LE would be byte-swapped wrong); `TestRawPassthroughReliesOnBigEndianRefusal` fails if that refusal is ever lifted. Two steps have no dicomtool equivalent. An optional **transfer syntax conversion** (`targetTS`), applied **last among the attribute steps** because decompression rewrites the attributes describing the pixels it produces, and profile-wide (never per modality); then **pixel masking** (`maskRegions`, see maskengine.go), which runs after it — masking needs native samples, which the conversion is what produces, and it writes no attribute so the conversion still has the final say over them. `maskingApplies` resolves the regions against the **header** before a frame is decoded, so a file no region applies to is never decompressed — without it, a profile masking a handful of images decompressed and re-encoded the whole study (measured on the 177-file echo study: 23 of every 25 files, a tenfold export, 75 s → 0.1 s for the same 25 files once skipped). It is deliberately generous — unknown dimensions or an unmaskable file return true, so the authoritative per-frame resolution in `applyPixelMask` still runs and still reports the failure. Masking a compressed file that *does* need it **forces a decompression the profile did not request**; the masked frames are then re-encoded per recompress.go — a lossless source back into its own syntax (`modifyResult.MaskRecompressed`), a lossy source into J2K Lossless with no added loss (`MaskRecodedLossless` — the field-measured alternative was a 16× uncompressed export), and only a source with no encoder path or a failed encode is written Explicit VR LE (`MaskDecompressed`) — each with its own summary clause, so the encoding never changes silently. A file the generous header gate admitted but the per-frame resolution then masked nothing on gets its original codestream restored verbatim. `mayMask` (profile-level or any override) therefore relaxes the write verification exactly as `targetTS` does. Per-modality mask regions **replace** rather than extend the profile's, since geometry describes one modality's screen layout. A source whose pixel data has no built-in decoder fails that file rather than exporting it in an unrequested syntax. `modifyWriteOpts` relaxes write verification to `SkipVRVerification`+`SkipValueTypeVerification` whenever a conversion is requested — emitting Explicit VR for elements parsed under Implicit VR would otherwise fail files that write fine untouched. A third has no dicomtool equivalent either: an optional **DICOMDIR index** (dicomdir.go), requested via `modifyParams.dicomdir`. Every worker collects one `dicomdirSource` from the in-memory transformed dataset of each file it successfully writes (no second parse), and once `wg.Wait()` returns, `runModificationImpl` builds the index once from everything collected — for whatever a cancelled or partially-failed run did write — and either writes it as `outDir/DICOMDIR` or, when writing into a zip archive, as a `"DICOMDIR"` entry via `zipSink.writeRaw` (raw bytes, no `sdicom.Write` — the entry is already a complete, offset-patched file). A DICOMDIR failure (`modifyResult.DicomdirWritten`/`DicomdirError`) never fails the run — the exported DICOM files are unaffected — except that `runModificationToZip`'s own finalize-failure path clears both fields too: an archive lost to a rename or close failure takes any DICOMDIR entry it held down with it, and a written-then-lost index must not be reported as written. **Each worker's per-file closure recovers panics** and routes them through `recordFailure`: `safeParse` (dicomsafe.go) already demotes a parse panic to an error, but decode, mask, re-encode and write all reach library and cgo code that can panic on a malformed file, on a goroutine where that kills the process — so a panicking file becomes one more line in the failure dialog instead. The recover closes and removes the half-written output first (Windows will not delete an open file, and a panic skips the normal `Close`); a zip run leaves no partial entry, since a file is fully encoded before anything of it reaches the archive. `processFileFn` is the test seam for this, matching `encodeMaskedFrame` in recompress.go. **A run that can decompress (`mayMask || targetTS`) is admitted by weight as well as by count**: each worker weighs its file with `fileMemoryWeight` — a header-only read (`readDicomHeader`, which stops before the pixel data — the `SkipPixelData` parse it replaced read every pixel byte to discard it, so every file of such a run was read in full twice) through `projectedPixelBytes` (transcode.go, shared with the mask bench), times `modifyMemoryOverheadFactor` because the decoded frames, the re-encoded output and the snapshot's original codestream are all live at once — then acquires that from a `memBudget` and holds it **across the write**, since the decoded frames stay alive until `sdicom.Write` has serialised them. A header that will not parse weighs 0 and proceeds: `processFile` fails it properly a moment later, and inventing a weight for an unreadable file is worse than not gating it. **Every run now has the limiter**: a tag-only run weighs a file by its size on disk × `encodedCopies` (2 — parsed dataset with raw pixel bytes, plus the encoded output; 3 in a zip run, for zipSink's compressed copy), from a `Stat` of the already-open file, and pays for no header read; a decoding run adds that to `fileMemoryWeight`. **Worker count is `modifyWorkerCount`**: CPU-heavy runs (zip, masking, conversion) get half the logical processors clamped to [2, 8] — about one per physical core, leaving hyperthread siblings for the UI and other apps — tag-only folder exports keep min(4, NumCPU) (disk-bound; more readers mostly add seeking); `DICOMQR_MODIFY_WORKERS` overrides (1–64). It was min(NumCPU, 4) for everything — all of a 4-thread laptop, a quarter of a 16-thread workstation. **Workers run at below-normal CPU priority** (workerpriority.go), which is what makes the wider pool a good neighbour. The residual this section used to note — a tag-only run holding one parsed file per worker whatever the files' size — is closed by that size-based weight. `hasNestedTag` + `fileNotes.nestedDOBKept` → `modifyResult.NestedDOBKept` is the **evidence** half of the birth-date safeguard (modifyprofile.go holds the profile-shape half): measured on the finished dataset so it reports what actually ships — a profile that removed `0400,0561` no longer counts — and gated on the per-file effective `dobMask`, which both keeps the extra traversal off every other run and reflects that a nested birth date is only a surprise once the top-level one was rewritten. Deliberately broader than the advisory: it counts a birth date nested *anywhere*, so it also catches the residual case where `0400,0561` was removed but one nests elsewhere |
| `dicomdir.go` | DICOMDIR (PS3.10 File-set) builder, ported from dicomtool's `cmd/dicomdir.go` — pure `suyashkumar/dicom`, matching the [DICOM library policy](#dicom-library-policy). Two-pass: `buildDICOMDIRBytes` serialises the PATIENT→STUDY→SERIES→IMAGE `DirectoryRecordSequence` once with every offset field zeroed (`sdicom.Write`), locates each directory record's byte position by scanning for sequence-item start markers (`findSequenceItemPositions`), then patches the `OffsetOfTheNextDirectoryRecord`/`OffsetOfReferencedLowerLevelDirectoryEntity`/root first-and-last-record UL fields in place (`patchUL32`) — inherent to the format, since a record's offset can only be known once the file has been serialised once. The `pat*` patterns are **literal Explicit VR LE element headers**, so the builder asserts a byte-level encoding it cannot itself verify; `patchUL32` therefore reports whether it found its target and **every miss ends the build**. Nothing may be skipped: all `2 + 2N` patches must land, since even a leaf record carries both pointers holding 0. ## DICOM library policy

**suyashkumar/dicom owns everything application code does with DICOM files** — parsing, writing, presenting. **grailbio/go-dicom is an internal detail of the vendored netdicom stack** (Q/R element plumbing, DIMSE wire encoding, dicomlog) and must never be imported by new application code: it is archived with a pre-2018 data dictionary, so any path that re-encodes through it mistypes newer tags (e.g. 0018,9362 → UN → unencodable). The C-STORE push therefore sends stored dataset bytes verbatim (no parse/re-encode). Remaining grailbio usage (dicomnet.go Q/R elements, storagescp.go meta writer, main.go dicomlog) is contained legacy, **deliberately left in place**: it handles only pre-2018-stable machinery (self-authored query keys, the fixed meta group, mainstream SOP classes), and the Q/R plumbing embodies hard-won field fixes (Conquest negotiation, C-GET message-ID split). Do not migrate it without a concrete trigger — an inexpressible query key, a missing SOP class (fix by adding a UID constant to the vendored fork instead), a grailbio build breakage, or a demonstrated defect.

## Notes

- App ID: `com.jeffreyleal.dicomqr`
- Settings persisted to `~/.dicomqr/settings.json`
- C-MOVE requires the embedded C-STORE SCP listener (default port 11112) to receive files
- The local AE Title (default `DICOMQR`) must be registered on the PACS as a known destination
- The app "owns" the download folder: downloads, imports, and manual scans keep `.dicomqr-index.db` in sync with the folder contents, and touching a tree entry whose files were removed externally prunes it from both the tree and the index
- Modification (de-identification) profiles live in `~/.dicomqr/profiles.json`, seeded from `defaults/` on first run and never overwritten by seeding; the format and semantics largely match dicomtool, with these deliberate divergences: `zip`, `flat`, `transfersyntax`, `exportname`, `maskregions`, `nooverlays` and `ignoresopclass` are dicomqr-only (ignored by dicomtool, and dropped when it saves), dicomtool's `maskrows` is unsupported here (dropped on load, stripped on save — `maskregions` is its replacement, and masks rectangles rather than whole rows from the top), the `uid` suffix option is removed (the value is preserved through load/save and disclosed by the editors, but a profile carrying it is refused at run time in favour of Remap UIDs — never silently ignored), and **tag aliases are gone** — dicomqr no longer reads `tags.json`, so a dicomtool profile referring to tags by phrase (`PatientName=ANON`) must be recoded to `0010,0010=ANON` before it will compile here. The tag picker names tags from the standard dictionary, which made a user-maintained alias map a second naming authority with nothing left to do. An existing `~/.dicomqr/tags.json` is left on disk, inert. Profiles are managed in Preferences > Modification & Export — changes are written back only on Apply and only when something changed, and a profiles.json that fails to parse is never overwritten. Modified files always go to a user-chosen folder outside the download folder — the catalog is never touched
