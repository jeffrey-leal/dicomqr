# dicomqr

A Fyne-based Windows GUI application for querying and retrieving DICOM files from a PACS server.

## Build

Requires CGO and the mingw64 GCC toolchain. **Must be built from an MSYS2 MinGW64 terminal.**

JPEG 2000 decoding (`-tags openjpeg`) requires the OpenJPEG library, and JPEG Lossless decoding (`-tags jpeglossless`) requires libjpeg-turbo 3.x, each installed once with:
```bash
pacman -S --needed mingw-w64-x86_64-openjpeg2
pacman -S --needed mingw-w64-x86_64-libjpeg-turbo
```
Release builds enable both tags (`-tags "openjpeg jpeglossless"`; libopenjp2 and libjpeg are statically linked — single self-contained exe). Omitting a tag still builds; the corresponding files then report "support not built in" and suggest the external viewer.

All builds must pass `-extldflags=-static` so GCC links its own runtime (libwinpthread, libgcc) statically; without it the exe imports `libwinpthread-1.dll` and fails to start on machines without MSYS2.

Open MSYS2 MinGW64, then:

```bash
export PATH="/c/Program Files/Go/bin:$PATH"
cd /c/Users/jeffr/source/repos/dicomqr
```

Release build:
```bash
CGO_ENABLED=1 CC=/c/msys64/mingw64/bin/gcc.exe GOAMD64=v3 \
  go build -tags "openjpeg jpeglossless" -ldflags="-s -w -H windowsgui -extldflags=-static -X main.buildDate=$(date +%Y-%m-%d)" -o dicomqr.exe .
```

Development build (with debug info):
```bash
CGO_ENABLED=1 CC=/c/msys64/mingw64/bin/gcc.exe \
  go build -tags "openjpeg jpeglossless" -ldflags="-extldflags=-static -X main.buildDate=$(date +%Y-%m-%d)" -o dicomqr.exe .
```

## Project structure

| File | Purpose |
|---|---|
| `main.go` | App entry point, window layout, tab container, menu bar, connection panel, query panel, retrieve panel, status bar, connection/SCP LEDs |
| `resultsmodel.go` | `resultsModel` — tree data structure for C-FIND query results |
| `queryrow.go` | `queryRow` — Fyne widget for results tree rows (hover tooltip, right-click menu) |
| `dicomnet.go` | `DicomClient` — SCU wrapper for C-ECHO, C-FIND, C-MOVE, C-GET, C-STORE, Modality Worklist |
| `storagescp.go` | `StorageSCP` — embedded C-STORE SCP listener that receives C-MOVE deliveries. `patientFolderName`/`studyFolderName`/`seriesFolderName` are the one authority for the organized hierarchy's names (called by `organizeFilePath`, `resultsModel.localFolderFor` and `exportLayout.relFor`), and each ends in **`safePathComponent`**: a component that is nothing but dots is prefixed `_`, because `sanitize` strips none of the characters in `..` and `filepath.Join` then Cleans it — a `PatientName` of `..` used to write the received file one level *above* the download folder, through C-STORE, C-GET and Import alike. The whole-string dot test (not an exact `.`/`..` match) also covers `...`, which Windows cannot create at all, and can never rename a legitimate folder — which matters, since renaming one orphans everything already downloaded under it. `sanitize` itself is deliberately unchanged: it also builds file names, where a suffix makes traversal impossible, and any change to it would rewrite existing folder names. `organizeFilePath` then re-checks containment with `pathWithinDir` and falls back to the flat layout, so staying inside the download folder is a property of the function rather than of having got the character rules exactly right |
| `localbrowse.go` | Local Browse tab — scan download folder, push to PACS, delete local files, preview routing, Modification submenu. `parseLocalFileMeta` is the indexing read behind four call paths (this scan, the Import tab's source scan, and `catalog.ingestPaths` after every retrieve and every import), and it **stops reading once past `localMetaMaxGroup`** — `scanLocalFileMeta`, the technique `scpParseMetadata` uses. That matters because `SkipPixelData` does **not** avoid reading the pixels: the library's `Reader.Skip` is `io.CopyN(io.Discard, …)`, not a seek, so a full parse still pulls every pixel byte off the disk to discard it, making the old scan scale with study size rather than file count. Measured over 1,500 files totalling 13 GB: 6.4 MB read instead of all of it, 649 ms instead of 12.4 s (≈19×, and more than 8-way threading of the old path would have given — threading composes on top but is the smaller half). `localMetaMaxGroup` is **derived** from `localMetaTags` rather than written as `0x0020`: a tag later added in a higher group would otherwise sit past where the scan stops and read as absent from every file, silently. `fullLocalFileMeta` remains as the fallback for a file whose tags are not in ascending order — the standard requires that order and no measured file breaks it, but a missed identifier drops the file from the tree entirely, and the fallback never runs on a conformant file. Values are read with a checked assertion, not `sdicom.MustGetStrings`, which panicked outside the parse boundary's recover on a tag stored under an unexpected VR. `TestScanBench` (opt-in, `DICOMQR_SCAN_BENCH`) asserts the two paths agree file-for-file over a real study. **Progress is paced by `scanProgressInterval` (time), never by a file count**: both callers hand each report to `fyne.Do`, whose queue is unbounded and never blocks, so a per-N-files trigger emits at whatever rate the disk runs at and the UI goroutine must drain every one — each re-texting a width-changing label, which on Windows repaints the whole frame (see `stableMin`). Once the scan itself got ~20× faster the same ~500 updates arrived as a burst and the callback that populates the tree queued behind them, so the tree looked seconds slow when it was instant. **The scan reads files in parallel** (`scanWorkers`, default 8, `DICOMQR_SCAN_WORKERS`) in three phases — walk to collect paths, parse on a worker pool, merge in walk order. A cold scan is bound by *seek latency*: measured on a RAID-0 array of spinning disks, 35,489 files took 5½ minutes (9.3 ms each, one head movement) against 10 s warm, and after early exit the scan reads only a few KB per file, so those minutes are almost all waiting. Eight rather than the CPU count because these workers sleep on the disk where the modification and mask pools compute — and **provisional**, since cold conditions cannot be reproduced on a machine with enough RAM to cache the corpus; the override is how it gets settled. Each worker writes its own index in a `[]scanResult`, so **the merge runs in walk order**: first-write-wins study metadata and the file order inside a series are what the tree shows, and neither may depend on which worker finished first (`TestScanLocalFolderIsDeterministic`). The returned `studies`/`series` slices are sorted by UID — they come out of maps, so their order was randomised run to run even before any of this was parallel; harmless where they go, but not something to leave for the next caller. Progress reporting follows clipBuffer's split (workers only `atomic.Add`, one ticker goroutine publishes), and the phases make the total known up front, so the message is a bounded `N of M files`. **Local Browse's Scan runs `syncLocalFolder`, not `scanLocalFolder`**: it walks, compares each file against the catalog's stamps, and reads only what is new or changed, so an untouched folder opens no files at all and the walk is the whole cost — the difference between minutes and seconds on a cold disk. `walkDicomFiles` uses **`WalkDir`, not `Walk`**, because `Walk` `Lstat`s every entry while `WalkDir`'s `DirEntry.Info()` on Windows returns the data the directory enumeration already produced (verified in Go's source — a cached `*fileStat`, no syscall), so the size and mtime the comparison needs arrive free. It also **counts entries it could not read**, and `filesToRemove` prunes **nothing** when that count is non-zero: files under an unreadable subtree are indistinguishable from deleted ones, and an index briefly stale is recoverable where one that has silently dropped a study is not. `scanLocalFolder` remains the full read, used by the Import tab (an arbitrary source folder has no index to compare against) and by the **Rebuild** button, which keeps `replaceAll` — Scan now trusts the index, and suspecting the index is exactly why someone presses Scan |
| `catalog.go` | `catalog` — persistent SQLite index (`.dicomqr-index.db` in the download folder) backing the Local Browse tree; nil-safe, WAL, single connection. `fileStamps` reads back the per-instance `size`/`mtime` — written since the index was added and, until the incremental scan, never queried — which is what lets a re-scan skip a file: matching stamps mean the copy on disk is the one that was parsed. Resolution is one second (what the schema stores), so a file rewritten within the same second to exactly the same length would read as unchanged; dicomqr never edits its own downloads, and Rebuild is the recovery. `upsertMetas` is `ingestPaths`' counterpart for callers that already hold parsed results — a scan parses its changed files on a worker pool, and handing `ingestPaths` the paths instead would re-parse them serially |
| `modifyprofile.go` | Modification (de-identification) profiles — `ModProfile`, load/first-run seeding of `~/.dicomqr/profiles.json`, base-chain resolution, tag parsing/display names. **Every tag reference is canonical `GGGG,EEEE`**: `normalizeModProfile` canonicalises on load, and `mergeModProfiles` compares **parsed tags** (`tagMatchKey`/`setMatchKey`) rather than literal strings — a Keep list cancels its base's Removes by tag identity, so two files spelling one tag differently can no longer silently un-cancel a removal and delete a tag the user asked to preserve. An unparsable reference is kept verbatim for validation to report, never dropped. `validateSetValue` checks a Set value against the tag's VR (dates, times, UIDs, numerics, length limits; empty always allowed) — the engine's `buildElement` only ever coerced the numeric VRs, so a `DA` set to `ANON` used to reach the exported files. A Set value of exactly `[GGGG,EEEE]` is a **reference** to another of the same profile's Set values (`setValueReference`, `resolveSetReferences`, `setValueFollowers`): the shipped profile writes `0010,0020=[0010,0010]` so Patient ID follows the new Patient Name, a relationship the Modification dialog used to hold as hardcoded tag numbers. **A reference can never reach the value in the file being modified** — that would copy the real patient name forward into whatever field named it, per file, with nothing on screen to show it. One level only: a reference to a reference is an error, which rules out cycles by construction. `compileModifyParams` resolves before parsing, so the engine only ever sees literals. `modProfileTargetSyntax` maps the dicomqr-only `transfersyntax` field (same `explicit-le`/`implicit-le` tokens as the server profile) to the UID exports are written in, and the `tsExportLabel*` constants keep the profile editor and the Modification dialog naming it identically. **`modProfileDOBAdvisory` is the safeguard for the one thing the birth-date mask cannot reach**: `applyDOBMask` rewrites the top-level `0010,0030` only, where removals, date shift, UID remap and Set values all recurse. In ordinary image objects that suffices — demographics live in the top-level Patient Module, and the sequences referencing a patient (`0008,1120`, `0010,1002`) carry identifiers, not birth dates — but **Original Attributes Sequence (`0400,0561`)** nests the pre-modification values an earlier de-identification changed, so a study processed once before can ship the real birth date while the top-level field reads masked. Removing `0400,0561` takes its nested contents with it, which is why the shipped profiles are not exposed (`TestEmbeddedDefaultsRaiseNoDOBAdvisory` fails if that removal is ever dropped). The advisory must be given a **resolved** profile — a base supplies the removal for most real profiles and a Keep list can cancel it again — and reads only the profile-level Removes, since an override's removals cover its own modality alone. Making the mask recurse was rejected: `replaceInElements` writes one value at every depth, right for a Set rule but wrong for a mask, which has to be applied to each occurrence's own value. `Dicomdir` — a field dicomtool already defines, kept for JSON interop — requests a DICOMDIR (PS3.10 File-set) index alongside the export (dicomdir.go); profile-wide only, like `Zip`, and unlike dicomtool's own `dicomdir:true` it composes freely with `Zip` rather than refusing the combination. `Flat` writes every exported file directly into the export root instead of the patient/study/series hierarchy `exportLayout` otherwise builds, named after its SOP Instance UID rather than kept under its source name — dropping the folders drops the context a source name relied on for uniqueness, so flat mode cannot reuse it. Profile-wide only, like `Zip` and `Dicomdir`, and composes with both |
| `setvalues.go` | `setValueList` — the Set values row list (tag chosen from the picker + value entry + delete), replacing a free-text `TAG=VALUE` box in both profile editors. The owning window is `attach`ed after construction rather than passed in, because both editors build their controls before `openOwnedWindow` creates the window the picker parents to — and keeping construction window-free is what lets `validate()` be driven by tests with no canvas. Choose tags… opens the picker with the current tags checked, so it adds and (by unchecking) removes rows; a tag that stays keeps the value already typed. Rows keep the profile's stored order (a group-then-element sort was tried and reverted: the stored order is the author's presentation choice — shipped base-deident leads with Patient Name, not a blank Accession Number — and sorting made Apply rewrite an unedited profile reordered); picker additions append in dictionary order via `mergeTagSelection`, which keeps surviving rows in place, and a row whose reference does not parse stays where the profile put it, visible to be fixed. A value bracketed like a reference but naming no tag (`[patient name]`) is rejected rather than stored as a literal |
| `modifyengine.go` | De-identification engine ported from dicomtool `modify` (identical semantics): set/remove/keep, DOB mask, UID remap (the `uid` suffix option is removed — a profile still carrying it is refused at compile with a message naming Remap UIDs, never silently ignored, and the stored value round-trips untouched), overlay-plane removal (`nooverlays` drops groups 6000–60FE even — the bitmap channel no per-tag rule reaches and pixel masking cannot touch), date shifting (`shiftdays` — DA/DT at any depth, PatientBirthDate excluded), private-tag removal, fixvr, per-modality overrides; `runModification` worker pool writes to an export folder using the PHI-safe layout from `exportLayout` (the export root the user types in the Modification dialog stands in for the patient folder, or patient+study for a study-level run — the only names guaranteed to need typing, since a patient folder is always PHI; everything below keeps its source folder/file name **unless** the tag(s) that name is built from actually changed, in which case that one component is rebuilt with the same rules `organizeFilePath` uses, from `exportNames` read before and after the file's attribute steps — `processFile` captures both into `fileNotes`, so a shifted `StudyDate` or a replaced `SeriesDescription` moves the file into a correctly-renamed folder while an untouched study or series keeps its original name instead of a generic `study-NN`; a remapped SOP Instance UID likewise renames the file itself). `patientFolderName`/`studyFolderName`/`seriesFolderName` (storagescp.go) are the one place that naming scheme is defined — `organizeFilePath`, `resultsModel.localFolderFor` and `exportLayout.relFor` all call them rather than keeping their own copies. `exportLayout.flat` is the alternative to all of that: every file lands directly at the export root, named after its SOP Instance UID (`flatFileName`) rather than kept under its source name — the folder hierarchy a kept source name relied on for uniqueness is exactly what flat mode removes, so reusing the source name would reintroduce the collisions the hierarchy prevented. `flatNames` (a mutex-guarded set of names already handed out) exists only for what a unique-by-construction SOP Instance UID cannot rule out — a genuinely duplicated instance, or a file with none at all — appending a numbered suffix rather than silently overwriting the first claimant or, in a zip, producing two entries with the same name; a nil `*flatNames` (every non-flat `exportLayout`, and the engine's own `relFor` tests) reserves nothing. `runModificationToZip` runs the same pipeline into a single zip archive (parallel modify, serialized entry writes; temp-file + rename so a failed/empty run leaves no archive). Two steps have no dicomtool equivalent. An optional **transfer syntax conversion** (`targetTS`), applied **last among the attribute steps** because decompression rewrites the attributes describing the pixels it produces, and profile-wide (never per modality); then **pixel masking** (`maskRegions`, see maskengine.go), which runs after it — masking needs native samples, which the conversion is what produces, and it writes no attribute so the conversion still has the final say over them. `maskingApplies` resolves the regions against the **header** before a frame is decoded, so a file no region applies to is never decompressed — without it, a profile masking a handful of images decompressed and re-encoded the whole study (measured on the 177-file echo study: 23 of every 25 files, a tenfold export, 75 s → 0.1 s for the same 25 files once skipped). It is deliberately generous — unknown dimensions or an unmaskable file return true, so the authoritative per-frame resolution in `applyPixelMask` still runs and still reports the failure. Masking a compressed file that *does* need it **forces a decompression the profile did not request**; the masked frames are then re-encoded per recompress.go — a lossless source back into its own syntax (`modifyResult.MaskRecompressed`), a lossy source into J2K Lossless with no added loss (`MaskRecodedLossless` — the field-measured alternative was a 16× uncompressed export), and only a source with no encoder path or a failed encode is written Explicit VR LE (`MaskDecompressed`) — each with its own summary clause, so the encoding never changes silently. A file the generous header gate admitted but the per-frame resolution then masked nothing on gets its original codestream restored verbatim. `mayMask` (profile-level or any override) therefore relaxes the write verification exactly as `targetTS` does. Per-modality mask regions **replace** rather than extend the profile's, since geometry describes one modality's screen layout. A source whose pixel data has no built-in decoder fails that file rather than exporting it in an unrequested syntax. `modifyWriteOpts` relaxes write verification to `SkipVRVerification`+`SkipValueTypeVerification` whenever a conversion is requested — emitting Explicit VR for elements parsed under Implicit VR would otherwise fail files that write fine untouched. A third has no dicomtool equivalent either: an optional **DICOMDIR index** (dicomdir.go), requested via `modifyParams.dicomdir`. Every worker collects one `dicomdirSource` from the in-memory transformed dataset of each file it successfully writes (no second parse), and once `wg.Wait()` returns, `runModificationImpl` builds the index once from everything collected — for whatever a cancelled or partially-failed run did write — and either writes it as `outDir/DICOMDIR` or, when writing into a zip archive, as a `"DICOMDIR"` entry via `zipSink.writeRaw` (raw bytes, no `sdicom.Write` — the entry is already a complete, offset-patched file). A DICOMDIR failure (`modifyResult.DicomdirWritten`/`DicomdirError`) never fails the run — the exported DICOM files are unaffected — except that `runModificationToZip`'s own finalize-failure path clears both fields too: an archive lost to a rename or close failure takes any DICOMDIR entry it held down with it, and a written-then-lost index must not be reported as written. **Each worker's per-file closure recovers panics** and routes them through `recordFailure`: `safeParse` (dicomsafe.go) already demotes a parse panic to an error, but decode, mask, re-encode and write all reach library and cgo code that can panic on a malformed file, on a goroutine where that kills the process — so a panicking file becomes one more line in the failure dialog instead. The recover closes and removes the half-written output first (Windows will not delete an open file, and a panic skips the normal `Close`); a zip run keeps whatever entry fragment was written, still counted as failed. `processFileFn` is the test seam for this, matching `encodeMaskedFrame` in recompress.go. **A run that can decompress (`mayMask || targetTS`) is admitted by weight as well as by count**: each worker weighs its file with `fileMemoryWeight` — a header-only parse (`SkipPixelData` never touches the pixels, so it stays cheap on exactly the large files this exists for) through `projectedPixelBytes` (transcode.go, shared with the mask bench), times `modifyMemoryOverheadFactor` because the decoded frames, the re-encoded output and the snapshot's original codestream are all live at once — then acquires that from a `memBudget` and holds it **across the write**, since the decoded frames stay alive until `sdicom.Write` has serialised them. A header that will not parse weighs 0 and proceeds: `processFile` fails it properly a moment later, and inventing a weight for an unreadable file is worse than not gating it. A tag-only run builds no limiter and does not pay for the header read. Residual, deliberately not addressed: such a run still holds one parsed file per worker, so four very large uncompressed files remain four files in memory — long-standing, and proportional to a size visible on disk. `hasNestedTag` + `fileNotes.nestedDOBKept` → `modifyResult.NestedDOBKept` is the **evidence** half of the birth-date safeguard (modifyprofile.go holds the profile-shape half): measured on the finished dataset so it reports what actually ships — a profile that removed `0400,0561` no longer counts — and gated on the per-file effective `dobMask`, which both keeps the extra traversal off every other run and reflects that a nested birth date is only a surprise once the top-level one was rewritten. Deliberately broader than the advisory: it counts a birth date nested *anywhere*, so it also catches the residual case where `0400,0561` was removed but one nests elsewhere |
| `dicomdir.go` | DICOMDIR (PS3.10 File-set) builder, ported from dicomtool's `cmd/dicomdir.go` — pure `suyashkumar/dicom`, matching the [DICOM library policy](#dicom-library-policy). Two-pass: `buildDICOMDIRBytes` serialises the PATIENT→STUDY→SERIES→IMAGE `DirectoryRecordSequence` once with every offset field zeroed (`sdicom.Write`), locates each directory record's byte position by scanning for sequence-item start markers (`findSequenceItemPositions`), then patches the `OffsetOfTheNextDirectoryRecord`/`OffsetOfReferencedLowerLevelDirectoryEntity`/root first-and-last-record UL fields in place (`patchUL32`) — inherent to the format, since a record's offset can only be known once the file has been serialised once. The `pat*` patterns are **literal Explicit VR LE element headers**, so the builder asserts a byte-level encoding it cannot itself verify; `patchUL32` therefore reports whether it found its target and **every miss ends the build**. Nothing may be skipped: all `2 + 2N` patches must land, since even a leaf record carries both pointers holding 0. An unpatched offset would otherwise stay 0, which is a *structurally valid* DICOMDIR that parses, carries every name and UID, and reads as an **empty file-set** — wrong output that looks right, reported as written. The record-count check above it is a different guard (it catches the writer restructuring the sequence, and any false positive in the item-marker scan) and says nothing about whether the patches landed. `TestBuildDICOMDIRUnpatchableOffsetFails` corrupts each pattern in turn and fails if the build succeeds. Unlike dicomtool (which can rescan an output directory it never touched otherwise), dicomqr never re-parses the export tree: `extractDicomdirSource` reads a `dicomdirSource` straight from the dataset `processFile` already transformed, using dicomqr's own `datasetString`/`datasetTransferSyntaxUID` readers rather than a duplicate helper. `writeDICOMDIRFile` is the folder-export wrapper; the zip-export path writes the same bytes through `zipSink.writeRaw` instead (modifyengine.go) |
| `maskregion.go` | Pixel-masking regions — `MaskRegion` (the dicomqr-only `maskregions` profile field), validation, and resolution to pixel rectangles. Geometry is stored as **fractions of the image**, never pixels: one study mixes image sizes, and a rectangle measured on the 800×600 loop misses the banner on the 1024×768 capture. Rounding is **outward** (start floors, end ceils) — half a row of leftover text is still PHI. Two modes: `rect`, and `outside-us-regions`, which derives the mask from the file's own `SequenceOfUltrasoundRegions` (the calibrated region is stable where vendor banner geometry is not — the same sequence chapters.go reads). The ultrasound rule uses the **bounding box** of all regions, so a duplex study's two panes keep the gap between them, and counts regions of every data type (no vendor writes identity inside a calibrated region). A file with no such sequence is inert on a non-US modality (so a rule written for the echo series does not fail every CT in the same run); on a **US** file it falls back to the profile's own rectangles when it has any — those files are usually analysis/measurement screens worth keeping, and the banner still goes while the measurements stay — and fails only when there is no rectangle to fall back on. The substitution is never silent: `maskResolution.usFellBack` → `fileNotes.maskUSFallback` → `modifyResult.MaskUSFallback`, a per-file `logWarn`, and a clause in the completion summary, because such a file was masked by geometry measured elsewhere rather than by its own stated layout. An unrecognised mode is always an error — a mask rule that quietly does nothing is indistinguishable, in the export, from a profile that never asked for one. **`MaskScope` (`appliesto`) is how far a region reaches**: nil = every image (what a profile-editor rule means), or any combination of SOP Instance UID / modality / cols / rows / `usregion` (declared\|absent), all ANDed. Added because a rectangle drawn on one analysis screen was applying to the ten beside it *and* to a differently-shaped group — blanking report content the export existed to keep. `maskRects` filters on scope **first**, so a region that does not apply contributes nothing, not even its failure modes. **Scopes resolve against `maskSource`, a snapshot taken in processFile immediately after the parse — never against the live dataset.** Masking runs last, and the steps before it rewrite exactly what a scope keys on: UID remapping (which shipped `base-deident` enables) replaces SOP Instance UID, and a removal rule can delete Modality or the ultrasound region sequence. Resolving live meant every image-scoped region and every exemption silently stopped matching, and the uncalibrated ultrasound files left with nothing applying to them failed and vanished from the export — field-reported. `TestScopedMaskSurvivesUIDRemapping`/`TestExemptionSurvivesUIDRemapping` fail if the snapshot is ever taken later. Third mode `none` records "reviewed, needs no masking": it exists so an ultrasound image with no calibrated region and no applicable rectangle can be exported deliberately rather than failing, without weakening the rule for images nobody has looked at |
| `maskengine.go` | The only code in the application that writes pixel values. `applyPixelMask` mutates each native frame's raw sample slice **in place** — `PixelDataInfo.Frames` holds `*frame.Frame` whose `NativeData` is a pointer, and the writer reads that same slice back, so no element is rebuilt. Native pixel data only: the caller must have decompressed first (see processFile), and encapsulated input is an error rather than a silent skip. Sample indexing follows PlanarConfiguration — the parsing library fills its raw slice sequentially from the stream, so planar data is plane-major and indexing it as interleaved would colour-shift the image instead of blanking it. The fill is **photometric-aware black**, not a constant zero: MONOCHROME1's black is the maximum stored value, YBR_FULL's is `Y=0, Cb=Cr=half`, and PALETTE COLOR resolves the darkest LUT entry — a white or green box reads as an intact annotation rather than a redaction. Chroma-subsampled (`YBR_*_422`/`420`) native data is refused with an instruction to set an output transfer syntax, since its layout is not one triple per pixel. Performance harness: `DICOMQR_MASK_BENCH=<study folder> go test -tags "openjpeg jpeglossless" -run TestMaskBench -v .` reports the study's composition and times three workloads (tags only / one image scoped / every image) so a new modality can be characterised before assuming a cost is inherent. It admits files until their projected **uncompressed** size reaches a budget (2000 MB, `DICOMQR_MASK_BENCH_BUDGET_MB`) — one 240-frame SPECT file alone decompresses to ~500 MB — and always logs how many it left out. It asserts correctness (nothing fails, the scoped image really is masked, at most one file recompressed-or-decompressed in the scoped scenario) but never wall-clock thresholds, which only produce flaky failures. **The invariant: if masking was requested and cannot be carried out on a file that has pixel data, the file fails** — exporting it unmasked discloses exactly what the profile existed to remove, and nothing downstream would notice. A dataset with no pixel data is not a failure |
| `recompress.go` | Re-encoding after pixel masking — the write-side counterpart of transcode.go's decoders, and the only path that ever *encodes* a compressed syntax. `recompressTargetFor` decides what masked frames become: a lossless source (.90, .57/.70) goes straight back into its own syntax, and a **lossy source (.50/.51/.91) becomes J2K Lossless** — re-entering the lossy syntax would degrade every pixel a second time, while the lossless encode adds nothing beyond the decode masking forced (field-measured on the BRYAN echo study: ×2.1 vs the stored size where leaving uncompressed was ×16.5); the syntax change is disclosed under its own count (`MaskRecodedLossless`), never folded into the round-trip one (`MaskRecompressed`). **Every fresh codestream is decoded again and compared sample-for-sample** (`encodeAndVerifyFrame`, seam `encodeMaskedFrame` for tests): a mismatch — encoder clamping a nonconformant sample, an unexpected colour conversion — falls back to Explicit VR LE rather than shipping unproven pixels, so a bad encode can only ever produce the old behaviour, never a wrong export. `pixelStateSnapshot` (taken in processFile immediately before the forced decompression, i.e. after the profile's edits) carries the source TS plus the Photometric Interpretation / Planar Configuration a colour decode rewrites to RGB / 0 — restored on a same-syntax round trip so declaration matches content again (MCT follows the snapshot: YBR_RCT → reversible colour transform), while a cross-syntax recode instead **labels colour output YBR_RCT** to match the transform the encode applies and leaves greyscale attributes as the decode wrote them; it also holds the original PixelData element, restored **verbatim** when the per-frame resolution masks nothing — a file decompressed for nothing must not change bytes. All fallible work happens before the first dataset mutation, so a failure never leaves half a state. ## DICOM library policy

**suyashkumar/dicom owns everything application code does with DICOM files** — parsing, writing, presenting. **grailbio/go-dicom is an internal detail of the vendored netdicom stack** (Q/R element plumbing, DIMSE wire encoding, dicomlog) and must never be imported by new application code: it is archived with a pre-2018 data dictionary, so any path that re-encodes through it mistypes newer tags (e.g. 0018,9362 → UN → unencodable). The C-STORE push therefore sends stored dataset bytes verbatim (no parse/re-encode). Remaining grailbio usage (dicomnet.go Q/R elements, storagescp.go meta writer, main.go dicomlog) is contained legacy, **deliberately left in place**: it handles only pre-2018-stable machinery (self-authored query keys, the fixed meta group, mainstream SOP classes), and the Q/R plumbing embodies hard-won field fixes (Conquest negotiation, C-GET message-ID split). Do not migrate it without a concrete trigger — an inexpressible query key, a missing SOP class (fix by adding a UID constant to the vendored fork instead), a grailbio build breakage, or a demonstrated defect.

- `github.com/algm/go-netdicom` — DICOM networking (C-ECHO, C-FIND, C-MOVE SCU, C-STORE SCP/SCU, Worklist); vendored under `thirdparty/go-netdicom` with local patches for `QRLevelPatientStudyOnly`, `QRLevelWorklist`, and `commandset.Init` (now `sync.Once` + `init()`: it calls `tag.Add`, which **writes** the dictionary map every `tag.Find` reads, and upstream called it lazily from `Run`/`NewServiceUser` — a first association concurrent with the tag picker's dictionary probe is a fatal concurrent map read/write)
- `github.com/suyashkumar/dicom v1.1.0` — DICOM file parsing (local files, image rendering, annotation extraction)
- `github.com/grailbio/go-dicom` — DICOM dataset encoding used by the C-STORE SCU and SCP
- `github.com/sqweek/dialog` — native Windows file/folder picker
- `modernc.org/sqlite` — pure-Go SQLite (no CGO) for the Local Browse persistent index
- `github.com/catppuccin/fyne` — Catppuccin colour themes (Preferences > Colour theme). Do NOT add `fyne.io/x/fyne` as a dependency — it tracks Fyne's master branch and silently upgrades the pinned `fyne.io/fyne/v2`; the Adwaita colours are vendored in `adwaitatheme.go` instead

## Notes

- App ID: `com.jeffreyleal.dicomqr`
- Settings persisted to `~/.dicomqr/settings.json`
- C-MOVE requires the embedded C-STORE SCP listener (default port 11112) to receive files
- The local AE Title (default `DICOMQR`) must be registered on the PACS as a known destination
- The app "owns" the download folder: downloads, imports, and manual scans keep `.dicomqr-index.db` in sync with the folder contents, and touching a tree entry whose files were removed externally prunes it from both the tree and the index
- Modification (de-identification) profiles live in `~/.dicomqr/profiles.json`, seeded from `defaults/` on first run and never overwritten by seeding; the format and semantics largely match dicomtool, with these deliberate divergences: `zip`, `flat`, `transfersyntax`, `exportname`, `maskregions` and `nooverlays` are dicomqr-only (ignored by dicomtool, and dropped when it saves), dicomtool's `maskrows` is unsupported here (dropped on load, stripped on save — `maskregions` is its replacement, and masks rectangles rather than whole rows from the top), the `uid` suffix option is removed (the value is preserved through load/save and disclosed by the editors, but a profile carrying it is refused at run time in favour of Remap UIDs — never silently ignored), and **tag aliases are gone** — dicomqr no longer reads `tags.json`, so a dicomtool profile referring to tags by phrase (`PatientName=ANON`) must be recoded to `0010,0010=ANON` before it will compile here. The tag picker names tags from the standard dictionary, which made a user-maintained alias map a second naming authority with nothing left to do. An existing `~/.dicomqr/tags.json` is left on disk, inert. Profiles are managed in Preferences > Modification & Export — changes are written back only on Apply and only when something changed, and a profiles.json that fails to parse is never overwritten. Modified files always go to a user-chosen folder outside the download folder — the catalog is never touched
